## 1. 현재 파이프라인과 남은 문제

```text
① road 마스크  ② −car −plate  ③ 밝기임계  ④ 형태필터  ⑤ 세선화  ⑥ 하프  ⑦ 각도  ⑧ 병합
```

| # | 남은 문제 | 성격 |
|---|---|---|
| ① | **분리대를 차선으로 오검출** | 형태·각도·연속성이 차선과 동일 |
| ② | **차선을 절반쯤 미검출** | 차량 가림, 마모, ROI 누락 |

①이 더 위험하다. 미검출은 그 차선에서 판정을 안 할 뿐이지만, **분리대 오검출은
없는 위반을 만들어낸다.**

### 구간별 소요 시간 (8,880프레임 실측, 하프)

| 구간 | 시간 | 비중 |
|---|---:|---:|
| **④ 형태 필터** | **7.0분** | **35.5 %** |
| 모델 추론 | 4.8분 | 24.3 % |
| 그리기·인코딩 | 3.2분 | 16.3 % |
| ⑤ 세선화 | 1.7분 | 8.5 % |
| **⑥ 하프** | **0.7분** | **3.7 %** |
| 나머지 | 2.3분 | 11.7 % |
| 합계 | 19.7분 | |

**하프 변환 자체는 3.7 % 다.** 검출기를 바꾸는 것은 속도 대책이 아니다.

## 2. 드론 자체 움직임 실측 — 모든 판단의 전제

시간축을 쓰는 방법은 전부 "프레임 사이에 화각이 얼마나 변하는가"에 달려 있다.
**무작위 표본은 이걸 알려주지 않는다** — 연속 구간을 stride 1 로 뽑아 쟀다.

측정: `goodFeaturesToTrack` → `calcOpticalFlowPyrLK` → `estimateAffinePartial2D`
(RANSAC). 움직이는 차량은 소수라 이상치로 배제되고 배경에 맞춰진다.

| 구간(프레임) | 이동 px/frame | 회전 도/frame | 배율 %/frame | 상태 |
|---|---:|---:|---:|---|
| 500~560 | 1.48 | 0.003 | 0.123 | 정지 비행 |
| 2500~2560 | **13.18** | 0.017 | **1.198** | **이동 중** |
| 4500~4560 | **15.28** | 0.028 | **1.091** | **이동 중** |
| 6500~6560 | 1.29 | 0.008 | 0.072 | 정지 비행 |
| 8000~8060 | 1.16 | 0.005 | 0.051 | 정지 비행 |

**드론이 정지 비행과 이동을 오간다. 10배 차이다.** 표본 5곳 중 2곳이 이동 구간.

이동 구간의 누적치:

| | 1프레임 | 1초(30프레임) |
|---|---:|---:|
| 이동 | 15 px | **458 px** (화면 폭의 24 %) |
| 배율 | 1.2 % | 약 40 % |
| 회전 | 0.03도 | 0.9도 |

**회전은 무시해도 되지만 이동과 배율은 무시하면 안 된다.**
차선 폭이 5.8~27.9 px 이므로 **프레임당 15 px 는 차선 폭과 맞먹는다.**

### 보정 비용

| 해상도 | ms/frame | 전체 8,880장 | 1920 대비 오차 |
|---|---:|---:|---:|
| **480×270** | **5.1** | **0.8분** | **0.00 px** |
| 960×540 | 11.0 | 1.6분 | 0.08 px |
| 1920×1080 | 34.8 | 5.1분 | 기준 |

**480×270 으로 줄여도 결과가 같다.** 현재 19.7분에 4 % 추가면 된다.

## 3. 방법별 정리

### 3.1 ★★★★★ 자체 움직임 보정 + 시간축 누적

지금 초당 30장을 **매 장 처음부터** 계산하고 앞 프레임 정보를 버린다.

```text
프레임 100: 차선 7개
프레임 101: 차선 4개   <- 3개는 트럭에 가려졌을 뿐, 사라진 게 아니다
프레임 102: 차선 7개
```

**차선 도색은 지면에 고정돼 있다.** 자체 움직임을 보정해 정렬하면 여러 프레임의
증거가 겹쳐 쌓인다. 반대로 **차량은 움직이므로 번져서 표를 못 받는다.**

| 효과 | 대상 |
|---|---|
| 미검출 보완 (N 중 M 채택) | **문제 ②** |
| 한 프레임만 반짝하는 잡선 제거 | 정밀도 |
| 프레임 간 떨림 제거 | 표준편차 4.0 |
| 이전 위치 주변만 탐색 | 속도 |
| **차량 진행방향 판정의 전제** | **문제 ①** (3.2절) |

**단, 보정 없이 겹치면 안 된다.** 이동 구간에서 5장만 쌓아도 76 px 번진다.

### 3.2 ★★★★☆ 차량 진행 방향으로 분리대 판정 (3.1 선행 필수)

형태로 안 되는 것을 **움직임**으로 가른다.

```text
중앙분리대 = 양쪽 차량이 반대 방향으로 가는 경계
차선       = 양쪽 차량이 같은 방향으로 가는 경계
```

car 마스크가 있고 `calcOpticalFlowPyrLK` 도 있다. 통합 seg 모델의 값어치가
여기서 또 나온다.

**자체 움직임 보정이 필수다.** 차량과 드론의 화면상 속도가 같은 크기다.

```text
차량 (60 km/h)    약 22 px/frame
드론 (이동 구간)   약 15 px/frame
```

| | 왼쪽 차 | 오른쪽 차 | 판정 |
|---|---:|---:|---|
| 실제 | +22 | −22 | 반대 → 분리대 ✅ |
| 드론 +15 관측 | +37 | −7 | 우연히 성공 |
| **드론 +30 이면** | **+52** | **+22** | **같은 방향으로 오판** ❌ |

**한계**: 차가 없는 구간은 판정 불가. 시간축 누적으로 이전 판정을 유지한다.

### 3.3 ★★★☆☆ 방향성 형태학 열림 (속도 목적)

긴 막대 커널로 열림 연산을 여러 각도로 돌린다. 막대와 나란한 것만 살아남는다.

**④ 형태 필터(7.0분, 최대 병목)를 대체할 수 있다.**

```text
지금:  for 덩어리 in 75개:  minAreaRect(...)    <- 파이썬 루프
대안:  for 각도 in 12개:    morphologyEx(...)   <- C++ 루프
```

**주의**: 세장비 4.0 이 부챗살(30장 중 10장)을 잡아준 핵심이다. 방향성 열림이
같은 일을 하는지 **반드시 검증**해야 한다. 속도를 얻고 정확도를 잃으면 손해다.

### 3.4 ★★★☆☆ 능선 검출 (Hessian)

밝기를 높이로 보면 차선은 **가늘고 긴 산등성이**다. 헤시안(2차 미분)으로
"한 방향으로만 볼록한가"를 직접 잰다. **밝기가 아니라 모양으로 거른다.**

현재 ③번의 약점을 정면으로 친다.

| | 측정값 |
|---|---|
| 프레임별 후보 픽셀 비율 | **0.27 % ~ 5.09 %** (19배) |
| 부챗살 원인 | 노출 과다된 넓은 콘크리트가 "밝기 상위"에 포함 |

능선 검출은 **넓은 덩어리에 애초에 반응하지 않는다.** ③④를 한 번에 대체 가능.
σ 로 찾을 굵기를 지정하므로 드론 고도 변화는 다중 스케일로 대응한다.
`scipy.ndimage` 로 구현 가능 (`skimage` 는 이 환경에 없다).

### 3.5 ★★☆☆☆ BEV (조감도 변환) — 하향 조정

원근을 펴면 차선이 평행한 수직선이 되고, 열 히스토그램만으로 찾을 수 있다.
간격이 일정해져 물리 제약(차로 폭 3.5 m)을 쓸 수 있고, **침범 판정을 미터
단위**로 할 수 있다.

**하향 이유: 배율이 프레임당 1.2 % 변한다.**

```text
 1프레임 후:  1.2 %      5프레임 후: 6 % (1000px 에서 60px 오차)
30프레임 후: 40 %  -> 사용 불가
```

호모그래피를 매 프레임 새로 추정해야 하고, **그 추정이 틀리면 차선 위치가
통째로 어긋난다.** 지금 방식은 한 프레임이 틀려도 그 프레임만 나쁘다.

### 3.6 ★★☆☆☆ 그 밖

| 방법 | 대체 단계 | 평가 |
|---|---|---|
| **LSD** | ③④⑤⑥ | 임계 튜닝 불필요. 그러나 **분리대가 더 강하게 잡힌다**(에지가 뚜렷). 바로 사용 가능(OpenCV 5.0) |
| **소실점 제약** | ⑦ | 각도 20도 필터로 이미 상당 부분 해결됨. 분리대는 못 거름. BEV 재료로는 필요 |
| **연결요소 직접 그룹핑** | ⑤⑥⑧ | 2.4분 절감. 다만 **점선 잇는 규칙을 자작**해야 함 — `maxLineGap` 이 란삭과의 승부를 가른 요소였다 |
| **행 단위 스캔** | ⑥ | 국소성 내장. 우리 차선은 45~60도라 안 맞음. **BEV 이후에 최적** |
| EDLines / FLD | ⑥ | `opencv-contrib` 필요(OpenCV 5.0 과 충돌 위험). LSD 로 안 되는 게 될 이유 없음 |
| DBSCAN 군집화 | ⑧ | 임의 임계가 줄지만 효과 미미 |
| Radon 변환 | ⑥ | 하프의 연속 버전. 얻을 게 없음 |
| Gabor / Steerable | ③④ | 방향성 형태학과 목적 동일, 더 무거움 |

### 3.7 ★☆☆☆☆ 학습 기반 (seg 아님)

| 방식 | 설명 |
|---|---|
| 행 앵커 (UFLD, CLRNet) | "각 행에서 차선이 몇 번째 칸이냐" 분류. 매우 빠름 |
| 곡선 회귀 (PolyLaneNet) | 차선을 수식 계수로 예측 |
| 키포인트 (GANet) | 차선 위 점을 검출해 묶음 |

seg 는 아니지만 **셋 다 차선 라벨이 필요하다.** 지금 없는 것이 그것이다.

**프레임 하나만 보는 방법은 화각 변화와 무관하다.** 현재 하프 파이프라인이
안전했던 이유이기도 하다 — 세장비·각도 모두 스케일·회전에 강한 특징이다.

**순서는 하나로 정해진다.**

```text
1단계  자체 움직임 추정   (+0.8분, 480x270 으로 충분)
   |   이게 있어야
2단계  시간축 누적       -> 문제 ② 미검출
   |   이게 있어야
3단계  차량 진행방향 판정 -> 문제 ① 분리대
```

**1단계 하나가 남은 두 문제의 공통 전제다.**
