## 3. "점으로만 나온다" 는 오해다 — 시각화의 문제

예측 결과(`val_batch0_pred.jpg`)에 **점만 흩어져 보여** 모델이 선이 아니라
점을 낸다고 오해하기 쉽다. 그렇지 않다.

**pose 모델의 출력은 순서가 있는 키포인트 12개다.** 0번부터 11번까지 차례로
이으면 그것이 선이다. 라벨도 똑같은 형태로 들어갔다.

```text
모델 출력:  kp0 kp1 kp2 ... kp11        (순서 있음)
선으로 보려면:  kp0 - kp1 - kp2 - ... - kp11  로 이으면 된다
```

Ultralytics 기본 시각화가 점만 찍는 이유는 **`skeleton`(연결 관계)을 모르기
때문**이다. COCO 사람 자세는 "어깨-팔꿈치-손목" 같은 연결이 코드에 하드코딩돼
있지만, 우리가 만든 12점 차선에는 그런 정의가 없다.

**해결은 간단하다.** 추론 결과에서 키포인트를 순서대로 이어 그리면 된다.

```python
r = model(img)[0]
for kp in r.keypoints.xy:            # (선 개수, 12, 2)
    pts = kp.cpu().numpy().astype(int)
    cv2.polylines(vis, [pts], False, (0, 255, 0), 3)
```

> **다만 지금은 이어도 선이 안 된다.** 키포인트 자체가 부정확하기 때문이다
> (Pose mAP50 0.0026). 시각화를 고쳐도 성능 문제는 그대로다.
> **"점이라서 실패" 가 아니라 "점이 틀려서 실패" 다.**

## 4. 진단 — 원인 세 가지

`train_batch0.jpg` 와 `val_batch0_pred.jpg` 를 보고 갈랐다.

### 4.1 라벨과 변환은 정확하다 ✅

`train_batch0.jpg` 에서 **무지개색 점 12개가 차선 위를 정확히 따라간다.**
호 길이 균등 재샘플링과 방향 정렬이 의도대로 동작했다.
**이쪽은 원인이 아니다.**

### 4.2 데이터가 너무 적다 (심각도: 높음)

train 48장, 선 322개. 사전학습 가중치가 **사람 자세**로 학습된 것이라
드론 시점 차선은 완전히 다른 도메인이다. 48장으로는 적응이 안 된다.

Box mAP50 이 0.14 까지 오른 것은 "여기 뭔가 있다" 는 것까지는 배웠다는 뜻이다.

### 4.3 증강이 데이터를 망가뜨린다 (심각도: 중간)

기본값 `mosaic=1.0` + `scale=0.5` 가 겹쳤다.

```text
원본:   화면을 가로지르는 긴 차선
모자이크: 4장을 잘라 붙여 -> 차선이 1/4 로 잘림
스케일:  거기서 다시 0.5~1.5배 확대/축소
결과:   트럭 한 대가 화면을 채우고 차선 조각만 남는 타일이 다수
```

`train_batch0.jpg` 에 그런 타일이 눈에 띄게 많다.
**차선처럼 화면 전체를 가로지르는 구조물에 모자이크는 부적합하다.**

### 4.4 ❌ 철회 — "축정렬 박스가 구조적 한계" 는 틀렸다

처음에는 이렇게 적었다.

> 대각선 차선의 축정렬 박스는 면적의 90 % 가 차선이 아니고 **옆 차선 박스와
> 대량으로 겹친다.** 라벨을 늘려도 남는 구조적 한계다.

**실측해보니 겹치지 않았다.** 라벨 48장의 모든 차선 쌍(1,191개)에 대해
축정렬 박스 IoU 를 쟀다.

| 박스 IoU | 차선 쌍 |
|---|---:|
| 중앙값 | **0.000** |
| 평균 | 0.058 |
| ≥ 0.5 | 36쌍 (3.0 %) |
| **≥ 0.7** (기본 NMS 임계) | **1쌍 (0.1 %)** |

**NMS 가 진짜 차선을 지울 위험은 1,191쌍 중 1쌍뿐이다.**

이유는 단순하다. **차선들이 서로 평행하게 떨어져 있어 x 범위가 겹치지 않는다.**
박스가 성긴 것(면적의 90 % 가 배경)과 박스끼리 겹치는 것은 별개인데,
확인 없이 이어붙였다.

그림에서 박스가 포개져 보였던 것은 **다른 차선이 아니라 같은 차선의 중복
검출**이었다. 학습이 덜 된 증상이므로 데이터가 늘면 줄어든다.

> **교훈**: "구조적으로 불가능" 이라는 판단은 값이 비싸다 — 방향 전환을
> 부른다. 재기 전에는 그렇게 쓰지 않는다. 07 문서 8.3절("설명률")과
> 같은 종류의 실수다.

### C — CLRNet 계열은 비교용으로만

4.4 를 철회했으므로 **"박스 때문에 옮겨야 한다" 는 근거는 사라졌다.**

오히려 **클래스는 YOLO-pose 가 유리하다.** CULane 형식에는 차선 종류가 없고
(`.lines.txt` 는 좌표만, 세그 마스크는 차선 순번), CLRNet 헤드의 분류는
`nn.Linear(..., 2)` 로 "차선인가 아닌가" 뿐이다. 종류를 넣으려면 헤드를
추가해야 하고 데이터 경로까지 4개 파일을 손대야 한다.

환경 구성과 데이터 변환은 이미 끝나 있으므로
(`vision-det/CLRKDNet/`), **같은 48장으로 위치 정확도만 비교**하는 용도로
쓰는 것이 맞다. 위치에서 확연히 낫지 않으면 옮길 이유가 없다.
