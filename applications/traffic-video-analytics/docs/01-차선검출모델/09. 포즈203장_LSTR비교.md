### 차선 트래킹 설계 (`lane_pose_track.py`)

차선은 세상에 고정 → 화면 위치 변화는 **드론 움직임 탓**. 그래서 차량 MOT 와 달리
교차·ID 뒤바뀜이 없어 오히려 단순하다. 파이프라인:

1. **`--ego`**: 프레임 간 ORB 호모그래피로 드론 자체 움직임 추정 → 이전 트랙을 현재 프레임에 정렬 (`LANE_POSTPROCESS_08/09` 자체 움직임 실측과 같은 기법)
2. 키포인트 집합 평균거리로 **같은 클래스끼리** 그리디 매칭 (게이트 90px)
3. `min_hits=3` 프레임 연속 매칭돼야 **확정** → 한두 프레임짜리 오검출 억제
4. 놓친 트랙은 `max_misses=8` 프레임 **coast**(속도로 외삽, `~` 표시) 후 삭제 → 깜빡임 제거
5. 키포인트 **EMA 평활** (신규 0.4) → 떨림 제거
6. 같은 클래스 겹치는 트랙 **병합** (오래된 쪽 유지) → 중복 차선 방지

결과: raw 검출이 프레임마다 3~8개로 출렁여도 표시 차선은 8~9개로 안정, 전 구간 연결.

### 깜빡임 원인 두 가지 (참고)

1. **모델 신뢰도 낮고 불안정** (0.3~0.5, 임계 근처) → 데이터·학습 보강으로 완화 (지금 mAP50 0.40)
2. **프레임 간 연결 없음** → 트래킹으로 해결 (위). 데이터와 무관한 후처리

### 남은 트래킹 한계

- 병합 게이트가 세면 인접 차로가 하나로 합쳐질 수 있음 (지금 살짝 그럼)
- coast 중 차선이 실제로 굽거나 끝나면 직선으로 외삽돼 살짝 벗어남
- 칼만(등속) 대신 EMA 라 급회전 시 약간 뒤처짐 → 필요하면 교체

## 3. LSTR 비교 (같은 203장, `vision-det/LSTR/`)

`input 1280×720`, 8000 iter. `source/` 3곳 패치(eos_coef, aux_loss, grad clip) + 래퍼 필요.

| | LSTR | YOLO-pose |
|---|---|---|
| val Pose mAP50 | 자체지표 미구축, **육안상 나쁨** | **0.406** |
| 시각화 | 쿼리 20개 난사, 선 뭉침, 프레임당 클래스 쏠림 | 차선별 분리, 도색 위, 클래스 맞음 |
| 추론 속도 (GPU forward) | 10.5 ms | **1.3 ms** |
| `000205` 눕은 차선 | **구조적 불가** (`x=f(y)`) | 미검출 (데이터, 해결 가능) |
| 셋업 | source 패치 + 래퍼 + 신규 로더 | 기존 스크립트 그대로 |
| 학습 안정성 | 곡선손실 발산 → clip 필수, class_error 40% plateau | 안정 |

### 판정

LSTR 은 **실선/점선 네이티브** 하나 때문에 시도했으나, YOLO-pose 도 실선/점선이
네이티브였다 (클래스 못 하는 건 CLRKDNet). LSTR 의 남은 이점(키포인트 슬롯 정체성
문제 없음)은 실현되지 않았고, `x=f(y)` 구조 한계 + DETR식 본 학습 부담이 크다.

**YOLO-pose 로 확정.** LSTR 프로젝트는 환경·파이프라인만 남기고 중단.
