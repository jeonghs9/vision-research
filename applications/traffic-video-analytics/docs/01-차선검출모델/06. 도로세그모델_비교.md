> 최종 갱신: 2026-08-18

## 결론

**YOLO26s-seg @1024 를 쓴다.**

| | 근거 |
|---|---|
| 정확도 | test Box mAP50-95 **0.533** — 후보 중 최고 |
| 번호판 | Box mAP50 **0.854** — 트리거·OCR 의 핵심 클래스에서 최고 |
| 트래킹 | **BoT-SORT 등 6종 내장.** RF-DETR 은 직접 붙여야 한다 |
| 속도 | 전체 영상 8.4분 — RF-DETR(8.6분)과 **사실상 동률** |

**속도는 더 이상 선택 근거가 아니다.** 옵션을 맞추면 두 모델이 같다 (§1).
정확도와 **트래킹 생태계**가 남는 차이다.

**속도가 더 필요하면 모델이 아니라 파이프라인을 바꾼다.** 모델 축소·해상도 축소는
**실측상 효과가 없거나 역효과다** (§5.2).

| 적용 | 효과 |
|---|---|
| `--decode_width 1920` (YOLO·RF-DETR) | 2.2~3.5배 ✅ 적용 완료 |
| `--native_masks` (RF-DETR) | 3.1배 ✅ 적용 완료 |
| 다중 GPU 구간 분할 | N배 — 다음 단계 |

## 0. 이 표로 하면 안 되는 비교

**① EoMT 는 정확도 비교 불가.** 데이터셋(UAVid vs si_vietnam_drone), 라벨 출처(수동 vs
SAM3 자동), 클래스, 지표(mIoU vs mAP)가 전부 다르다. **속도만** 싣는다.

**② YOLO 와 RF-DETR 의 mAP 도 소수점까지 믿으면 안 된다.** 계산 구현이 다르고
(ultralytics 자체 구현 vs faster-coco-eval), **conf 조건도 다르다** (YOLO 0.25 vs
RF-DETR COCO 관례). 0.1 이상 차이는 의미가 있지만 0.02 수준으로 우열을 말하면 안 된다.

**③ 속도만 조건을 맞춰 쟀다 — 이건 비교해도 된다.**
같은 영상(`000157_T`), 같은 stride, 같은 출력 규격, V100 1장, 같은 파이프라인 구조.

> **단, native 마스크는 126×126 이라 화면에서 경계가 각져 보인다.** `bilinear` 로
> 확대하면 완화되지만 해상도 한계는 남는다. **마스크 경계로 침범을 판정할 계획이면**
> `--native_masks` 를 끄고 기본 경로(원본 해상도, 26.6분)를 써야 한다.

## 3. 정확도 — RF-DETR-Seg 2종

같은 test set, 캐시 데이터셋, COCO 평가 관례(conf 미고정).

| 모델 | Box mAP50 | **Box 50-95** | Mask mAP50 | **Mask 50-95** | road | car | plate |
|---|---:|---:|---:|---:|---:|---:|---:|
| **Small @504** | 0.6920 | **0.5087** | 0.6748 | **0.4398** | 0.2990 | **0.7050** | **0.5222** |
| Nano @312 | 0.5671 | 0.3814 | 0.5351 | 0.3247 | 0.2554 | 0.6152 | 0.2736 |

클래스별은 AP 50:95.

**Nano 는 해상도를 38 % 줄여 속도 19 % 를 얻고 정확도 25 % 를 잃는다.**
특히 **plate −48 %** (312 에서 번호판이 약 5×2 px).

**RF-DETR 은 마스크가 강하다** — Mask mAP50-95 0.4398 로 YOLO s@1024(0.312)보다 높다.
해상도가 절반인데도 그렇다. 다만 conf·구현이 달라 직접 비교는 아니다.

**road 가 양쪽 다 최하위이고 RF-DETR 이 특히 약하다** (Recall 0.387).
DETR 계열은 쿼리 100개로 **개체**를 잡는 구조라 화면 절반을 덮는 단일 영역에 불리하다.

> **재확인 필요** — 이 road 수치는 4K 입력 전처리 문제였을 가능성이 있다.
> 영상 추론에서 입력을 1080p 로 바꾸자 road 픽셀이 7.89 % → 41.52 % 로 늘었다.
> 학습을 짧은변 640 캐시로 했으므로 1080p 입력이 학습 조건에 더 가깝다.

## 5. 이번 실험에서 확인된 것 — 속도의 진짜 병목

### 5.1 모델은 전체의 10 % 남짓이다

`predict()` 내부를 쪼개 잰 결과 (프레임당 ms).

| | 전처리 | forward | 후처리 | 전처리 비중 |
|---|---:|---:|---:|---:|
| YOLO s@1024 | **60.7** | 9.7 | 2.9 | **82 %** |
| RF-DETR S@504 | **407** | 32 | — | **93 %** |

**RF-DETR 의 모델 자체(32 ms)는 오히려 YOLO(38.5 ms)보다 빠르다.**
느렸던 이유는 8.3 MP 를 파이썬 경로로 리사이즈했기 때문이다.

### 5.2 모델 크기를 줄여도 속도가 안 변한다

YOLO 4종을 4K 경로로 재면 0.137~0.142 로 **사실상 같다** (최대/최소 1.04배).
GFLOPs 가 34.3 → 3.4 로 10배 줄어도 그렇다.

순수 forward 만 재면 이유가 보인다.

| 배치 | s | n | 비율 |
|---:|---:|---:|---:|
| **1** | 9.9 ms | 10.3 ms | **0.96×** |
| 32 | 126.6 ms | 61.9 ms | 2.05× |

**배치 1 에서는 s 와 n 이 같다.** 층이 139개로 동일해 GPU 지시 횟수가 같고,
각 지시의 준비 비용이 계산 시간보다 커서 연산량 차이가 묻힌다.

> YOLO 의 n/s 는 층을 줄인 게 아니라 **층을 얇게** 만든 것이다.
> `139 layers` 로 동일하고 파라미터만 10.37 M → 2.69 M.

### 5.3 fp16·compile 도 안 먹힌다

RF-DETR 최적화 실측 (추론 구간만).

| 변형 | 배속 |
|---|---:|
| `inference(fp16)` | **1.03×** |
| `+ batch 8` | 1.14× |
| `compile=T, fp16, batch 8` | **1.19×** |

RF-DETR 문서는 "fp16 으로 T4 에서 ~8배" 를 안내하지만 **실측 1.03배**다.
fp16 은 GPU 가 연산에 묶여 있을 때만 효과가 나는데, 여기서는 연산이 병목이 아니다.

### 5.4 효과가 있었던 것 — `--decode_width 1920`

ffmpeg 가 디코딩하며 1080p 로 축소해 보내면 4K 리사이즈가 사라진다.
**출력이 어차피 1080p 라 화질 손실도 없다.**

| 모델 | 4K 경로 | **1080p 경로** | 배속 |
|---|---:|---:|---:|
| YOLO s@1024 | 0.137 | **0.062** | 2.2× |
| YOLO n@1024 | 0.137 | 0.053 | 2.6× |
| YOLO s@640 | 0.142 | 0.048 | 3.0× |
| YOLO n@640 | 0.139 | 0.054 | 2.6× |
| **RF-DETR S@504** | **0.626** | **0.181** | **3.5×** |

검출 손실은 작다 — YOLO 640 모델 −0.5 %, 1024 모델 −3 %, **RF-DETR 은 +2.4 %(증가)**.

### 5.5 stride 를 낮추는 비용은 3배보다 싸다

압축 영상은 프레임을 건너뛸 수 없어 stride 3 에서도 전 프레임을 디코딩하고 2/3 을 버린다.
stride 1 은 그 버리던 것까지 쓰므로 디코딩이 공짜로 딸려온다.

| | decode 비중 | stride 3 → 1 |
|---|---:|---|
| YOLO s@1024 | 8.4 % | 0.062 → 0.056 (**−10 %**) |
| RF-DETR S@504 | 2.5 % | 0.181 → 0.180 (변화 없음) |

**이득의 크기는 decode 비중에 비례한다.**

## 6. 예측이 틀린 기록

| 예측 | 실제 |
|---|---|
| "1024 에서 번호판 13×6 px → 검출 어려울 것" | Box mAP50 **0.854** — 3클래스 중 최고 |
| "504 에서 번호판 8×3 px → 사실상 불가능" | AP 0.522, Precision **0.9008** |
| "road 는 큰 객체라 쉬울 것" | **양쪽 모델 모두 road 가 최하위** |
| "ffmpeg 축소로 잃는 건 번호판일 것" | **road 가 −21 % 로 가장 크고**, 표본에 번호판은 0개였다 |
| "RF-DETR 1080p 적용 시 0.082 s/frame" | 실제 **0.181**. 벤치마크를 메모리 상주 프레임으로 재서 파이프라인과 조건이 달랐다 |
| "RF-DETR 이 YOLO 의 1.3~1.7배로 좁혀질 것" | 실제 **3.2배** |

**작은 객체 성능을 픽셀 크기만으로 단정해 두 번 연속 틀렸다.** 번호판은 흰 사각형이라
형태가 단순하고 차량 뒷면이라는 맥락이 일정해서 작아도 잘 찾는다.
