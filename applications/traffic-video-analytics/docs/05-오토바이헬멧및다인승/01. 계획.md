## 1. 무엇을 만드는가

드론 뷰 교통 영상에서 **오토바이 관련 위반 2종**을 잡는다.

| # | 판정 | 정의 |
|---|---|---|
| ① | **다인승(2인 이상 탑승)** | 오토바이 1대에 사람 2명 이상이 올라타 있음 |
| ② | **헬멧 미착용** | 오토바이에 탄 사람 중 헬멧을 쓰지 않은 사람이 있음 |

**판정 대상은 오토바이 탑승자로 한정한다.** 보행자, 자전거 이용자, 차량 탑승자는
헬멧을 안 썼어도 위반이 아니다. 즉 **오토바이와 연관된 사람만 헬멧 판정 대상**이며,
연관에 실패한 사람은 판정 자체를 하지 않는다.

둘 다 **"객체 하나"가 아니라 "객체들의 관계"** 다. 그래서 탐지 모델이 직접
"위반"을 출력하는 게 아니라, **탐지 → 연관(association) → 판정** 3단계로 나눈다.

> **초급자 설명:**
> 탐지 모델은 "여기 사람이 있다", "여기 오토바이가 있다" 처럼 **개별 물체**만 찾는다.
> "이 사람이 저 오토바이에 타고 있다" 는 정보는 모델이 주지 않으므로,
> 박스 위치가 겹치는지를 코드로 따져서 우리가 직접 이어붙여야 한다.
> 이 이어붙이는 작업을 연관(association)이라고 부른다.

## 3. 왜 재학습이 필요한가

현재 모델에 **헬멧 클래스가 없다.** 헬멧은 다음 이유로 기존 클래스에서 유도할 수 없다.

- `person` 박스는 몸 전체를 감싸므로 머리 영역이 따로 나오지 않는다.
- 드론 뷰에서는 사람이 작게 찍혀 크롭 후 별도 분류기를 붙여도 해상도가 부족하다.

따라서 **헬멧 클래스를 포함한 새 스키마로 탐지 모델을 다시 학습**한다.

## 4. 클래스 스키마 — 3가지 안

헬멧을 어떻게 클래스로 표현하느냐가 이후 전부를 결정한다.

| 안 | 클래스 구성 | 미착용 판정 방식 | 장점 | 단점 |
|---|---|---|---|---|
| **A** | 기존 4 + `helmet` (5클래스) | 사람 머리 부근에 helmet 박스가 **없으면** 미착용 | 라벨링 단순 | **"없음"을 근거로 판정** → 미탐 1건이 곧 오탐. 머리 위치 추정도 필요 |
| ~~B~~ | ~~기존 4 + `helmet` + `no_helmet` (6클래스)~~ | ~~`no_helmet` 박스를 직접 탐지~~ | — | **미도입 확정.** 맨머리 라벨을 새로 만들어야 하고 기존 데이터 전량 재라벨이 필요하다 |
| **C** | 기존 4 + `motorcycle_2rider` 등 위반 자체를 클래스로 | 모델이 위반을 직접 출력 | 후처리 없음 | 조합 폭발, 데이터 희소, 규칙 변경 시 재학습 |

### 확정: A안 (5클래스) — 2026-08-25

```yaml
nc: 5
names:
  0: person
  1: car
  2: motorcycle
  3: plate_number
  4: helmet        # 헬멧을 쓴 머리
```

기존 0~3번 ID를 **그대로 유지**한다. 기존 라벨 파일을 건드리지 않아도 되고,
`det-best.pt` 로 만든 결과와 비교 분석도 가능하다.

**`no_helmet`(맨머리) 클래스는 만들지 않는다 — 확정이다.** 이후 성능이 부족하더라도
클래스를 늘리는 방향으로 돌아가지 않고, 데이터·임계·해상도로 해결한다 (8장·12장).

### 라벨링 기준 ≠ 판정 대상 — 반드시 구분할 것

혼동하기 쉬운 지점이다.

| | 기준 |
|---|---|
| **라벨링 (학습용)** | 이미지에 보이는 **헬멧을 전부 라벨**한다. 오토바이 탑승자든 아니든 상관없다 |
| **판정 (추론 후처리)** | **오토바이와 연관된 사람만** 헬멧 착용 여부를 따진다 |

라벨링에서까지 "오토바이 탑승자의 헬멧만" 으로 좁히면, 라벨 안 된 헬멧이 배경 정답이
되어 5장의 부분 라벨 오염이 발생한다. **탐지 모델은 헬멧이라는 물체를 배우게 하고,
"누구의 헬멧인지" 는 후처리에서 가린다.**

> **초급자 설명:**
> 모델에게 "오토바이 탄 사람이 쓴 헬멧만 찾아라" 를 가르치는 건 사실상 불가능하다.
> 헬멧 하나만 보고는 그 사람이 오토바이를 탔는지 알 수 없기 때문이다.
> 그래서 모델은 "헬멧" 만 찾게 두고, 오토바이와 이어붙이는 일은 코드가 한다.

### A안이 안고 가는 구조적 약점과 대응

A안은 헬멧 미착용을 **부정 근거(negative evidence)** 로 판정한다.
"helmet 박스가 없으면 미착용" 이므로, **헬멧을 쓴 사람인데 모델이 헬멧을 놓치면
그 즉시 미착용 오탐**이 된다. 드론 뷰에서 헬멧은 10~30 px 로 작아 미탐이 잦다.

> **초급자 설명:**
> "있는 것을 찾는" 판정과 "없는 것을 확인하는" 판정은 실패 방식이 다르다.
> 전자는 못 찾으면 그냥 놓친 것(미탐)으로 끝나지만, 후자는 못 찾은 것이 곧
> "위반이다"라는 **적극적 오답**이 된다. A안은 후자여서 헬멧 재현율이 낮으면
> 없는 위반을 만들어낸다.

이 약점은 스키마로 막을 수 없으므로 **후처리와 지표로 방어**한다.

| 방어 | 내용 | 위치 |
|---|---|---|
| ① 핵심 지표 전환 | `helmet` 의 **재현율**이 최우선 지표다. 이 값이 낮으면 오탐이 곧바로 늘어난다 | 8장 |
| ② 헬멧 전용 낮은 conf | 헬멧 클래스만 conf 임계를 낮게 잡아 미탐을 줄인다 (오탐 증가는 ③ 이 흡수) | 9.3 |
| ③ 연속 프레임 확정 | 단일 프레임 미검출로 위반을 확정하지 않는다. N 프레임 연속일 때만 확정 | 9.4 |
| ④ 판정 보류 구간 | 사람 박스가 너무 작거나 가려진 경우 위반이 아니라 **판정 불가**로 뺀다 | 9.3 |

헬멧 재현율이 낮아 오탐이 과다한 경우의 개선 경로는 **클래스 추가가 아니라**
① 헬멧 conf 하향 → ② 드론 뷰 헬멧 라벨 추가 → ③ 타일링 추론 → ④ imgsz 상향 이다
(8장·12장).

C안은 유보한다. "2인 탑승"과 "헬멧 미착용"이 곱해지면 클래스가 늘고, 3인 탑승 같은
경우를 커버하지 못한다. 판정 규칙은 코드로 두는 편이 수정 비용이 낮다.

## 5. 가장 큰 위험 — 부분 라벨 오염

이 작업에서 조용히 망하는 지점은 여기다.

두 데이터 소스를 그냥 합치면 이렇게 된다.

| 데이터 | person | car | motorcycle | plate | helmet |
|---|:---:|:---:|:---:|:---:|:---:|
| 기존 COCO_*_LABELING | ✅ | ✅ | ✅ | ✅ | ❌ 없음 |
| Roboflow 헬멧 데이터 | △ 일부만 | △ | △ | ❌ | ✅ |

YOLO 학습에서 **라벨이 없는 영역은 "배경"으로 간주된다.** 즉,

- 기존 데이터에 헬멧이 찍혀 있는데 라벨이 없으면 → "헬멧은 배경이다" 라고 학습한다.
- Roboflow 이미지에 자동차가 찍혀 있는데 라벨이 없으면 → "자동차는 배경이다" 라고 학습한다.

두 방향 모두 일어나며, **학습은 에러 없이 잘 돌아가고 mAP도 그럴듯하게 나온다.**
망가진 것은 배포 후에야 드러난다.

> **초급자 설명:**
> 라벨 파일에 적힌 박스만 "정답 물체"이고, 나머지 픽셀은 전부 "여기엔 아무것도 없다"는
> 정답으로 쓰인다. 그래서 **빠뜨린 라벨은 단순한 누락이 아니라 틀린 정답**이 된다.
> 모델은 "찾지 마라" 를 학습하게 되고, 그 클래스의 재현율이 무너진다.

### 대응 — 양방향 보충

```text
Roboflow 헬멧 데이터  ──▶ SAM3 로 person / car / motorcycle / plate 자동 보충
기존 COCO_* 데이터    ──▶ helmet 을 어떻게든 채워야 함  ← 6.4 에서 다룸
```

## 6. 데이터 파이프라인

### 6.1 Roboflow 데이터 수집 요건

수집 시 아래를 확인한다.

| 확인 항목 | 왜 |
|---|---|
| **뷰 각도** | 드론(하향) 뷰가 있는지. 대부분의 헬멧 데이터셋은 지상 CCTV·정면 뷰다 (→ 6.4 도메인 갭) |
| 클래스 정의 | `helmet` 이 **머리 영역**인지 **헬멧 물체**인지. 데이터셋마다 다르다 → 우리는 **헬멧 물체**로 통일 |
| `Without Helmet` 처리 | 5클래스 확정이므로 **맨머리 라벨은 버린다.** 단, 그 이미지 자체는 학습에 쓴다 |
| **안전모 데이터 배제** | Roboflow 에서 `helmet` 으로 검색하면 **공사장 안전모(hard hat)** 데이터셋이 대량으로 나온다. 색·형태·배경이 오토바이 헬멧과 다르고 교통 장면도 아니다. **수집 대상에서 뺀다** |
| 자전거 헬멧 | 형태가 유사하므로 포함해도 무방하다. 판정 단계에서 오토바이 연관으로 걸러진다 |
| 라이선스 | 재배포·상용 가능 여부 |
| 중복 | 여러 데이터셋이 같은 원본을 재업로드한 경우가 많다. split 간 누수 위험 |
| 이미 라벨된 클래스 | person/motorcycle 이 함께 라벨돼 있으면 SAM3 보충량이 줄어든다 |

다운로드는 **YOLO 형식**으로 받고, `data.yaml` 의 클래스 순서를 반드시 확인한다.
Roboflow 는 알파벳 순으로 ID를 부여하는 경우가 많아 **우리 스키마와 ID가 다르다.**
→ 리맵 스크립트 필요 (`scripts/05-오토바이헬멧및다인승/remap_roboflow_labels.py`, 신규).

기존 스크립트를 그대로 쓴다. 클래스 ID가 이미 일치한다(2장).

**주의: SAM3 결과를 그대로 정답으로 쓰지 않는다.** 자동 라벨은 다음이 흔하다.

- 군중에서 사람 여러 명을 한 박스로 묶음
- 번호판을 창문·표지판과 혼동
- 작은 오토바이 미탐

→ 6.3의 병합 규칙과 6.5의 검수를 반드시 거친다.

### 6.3 라벨 병합 규칙

같은 이미지에 **사람이 만든 Roboflow 라벨**과 **SAM3 자동 라벨**이 동시에 존재한다.

```text
우선순위:  사람 라벨(Roboflow)  >  SAM3 자동 라벨

병합 절차:
  1. Roboflow 라벨을 우리 스키마 ID로 리맵 → 그대로 채택
  2. SAM3 라벨 중, 같은 클래스의 Roboflow 박스와 IoU ≥ 0.5 인 것은 버림(중복)
  3. 남은 SAM3 박스만 추가
  4. helmet 은 SAM3 로 만들지 않는다 (Roboflow 정답만 사용)
  5. Roboflow 의 no_helmet / head / Without Helmet 라벨은 버린다 (5클래스 스키마)
```

4번이 중요하다. 헬멧은 이 프로젝트의 **핵심 정답**이므로 자동 라벨로 오염시키지 않는다.

### 6.4 기존 데이터의 helmet 결손 처리 — 3안 비교

기존 COCO_*_LABELING 데이터에는 헬멧 라벨이 전혀 없다. 그대로 합치면 5장의 오염이 발생한다.

| 안 | 방법 | 비용 | 위험 |
|---|---|---|---|
| **가** | 기존 데이터에서 **오토바이가 등장하는 이미지만 골라** helmet 을 수동 라벨 | 중 (대상 수만큼) | 낮음 |
| **나** | 기존 데이터에서 **오토바이가 없는 이미지만** 학습에 사용 | 낮음 | motorcycle 학습량 급감 |
| **다** | 클래스별 손실 마스킹(partial-label-aware) 구현 | 높음 (loss 수정) | 구현 난이도, 검증 부담 |

**권장: 가 + 나 혼합.** 기존 데이터에서 `motorcycle` 라벨이 있는 이미지만 추려
(그 수는 전체 대비 작을 것) helmet 을 수동 보충하고, 나머지는 그대로 쓴다.
오토바이가 없는 이미지에는 헬멧도 거의 없으므로 오염이 사실상 발생하지 않는다.

> 실제 수량은 `motorcycle` 라벨 보유 이미지를 세어봐야 정해진다 (→ 10장 1단계).

### 6.5 도메인 갭 — 지상 뷰 vs 드론 뷰

Roboflow 헬멧 데이터 대부분은 **지상 CCTV·정면·근거리** 영상이다. 우리 입력은 **드론
하향 뷰·원거리**다. 차이는 다음과 같다.

| | Roboflow 일반 헬멧 데이터 | 우리 드론 영상 |
|---|---|---|
| 카메라 각도 | 정면·측면 | 하향 (top-down) |
| 머리 형태 | 얼굴이 보임 | **정수리만 보임** |
| 헬멧 픽셀 크기 | 수십~수백 px | **10~30 px 추정** |
| 배경 | 도로변, 근접 | 도로 전체 |

정수리만 보이는 각도에서 헬멧과 맨머리 구분은 **색·질감·광택**에 의존한다.
지상 뷰만으로 학습한 모델이 드론 뷰에서 동작할 것으로 기대하면 안 된다.

**대책:** 우리 드론 영상에서 오토바이가 등장하는 프레임을 추출해 **소량이라도
직접 라벨링**하여 학습·검증에 넣는다. 특히 **val/test 는 드론 뷰로만 구성**한다.
지상 뷰 데이터로 val 을 만들면 지표가 실제 성능을 과대평가한다.

프레임 추출은 기존 스크립트를 쓴다.
`vision-seg/sam3/scripts/05-오토바이헬멧및다인승/extract-frames.py`

## 7. 데이터셋 구성과 검증 (워크스페이스 규칙)

```text
workspace/dataset/det/rider-safety/
├── RAW_SOURCES.md      # 원본 출처·버전·라이선스·클래스맵 기록 (필수)
├── raw/                # 수정 금지
│   ├── roboflow-<프로젝트명>-v<버전>/   # 다운로드 그대로. Roboflow 분할 구조 유지
│   └── drone-frames/                    # 우리 영상에서 뽑은 프레임
├── processed/          # 리맵·SAM3 보충·병합 결과
└── splits/
    ├── images/{train,val,test}/
    ├── labels/{train,val,test}/
    ├── vis/            # test split 무작위 30장 시각화 (필수)
    └── SPLIT.md        # 생성일·스크립트·원본경로·분할단위·통계·근거·검증결과
```

**경로 주의:** 워크스페이스 가이드 문서는 `datasets/` 로 적고 있으나 **실제 디렉터리는
`dataset/` (단수)** 이고 `det/ seg/ etc.` 로 분야가 나뉘어 있다. 가이드의 이름 변경은
아직 "검토" 상태다. 현행 구조를 따라 `dataset/det/` 아래에 둔다.

**Roboflow 가 나눠준 `train/valid/test` 를 우리 분할로 채택하지 않는다.**
`raw/` 안에 원본 그대로 두고, `splits/` 에서 새로 나눈다. 이유는 두 가지다.

1. 근접 중복 프레임이 Roboflow 분할의 train 과 test 에 흩어져 있을 수 있다 (누수)
2. 우리 val/test 는 **드론 뷰 전용**이어야 한다 (6.5)

**필수 규칙 2가지 (`workspace/CLAUDE.md`)**

1. **`vis/` 30장 + `SPLIT.md` 는 필수.** 라벨 변환은 조용히 틀린다
   (클래스 ID 밀림 ← 이번 작업에서 특히 위험, 좌표 뒤집힘). 시각화로 눈으로 확인한다.
   패널 구성: 전처리가 없으므로 **2분할(이미지 | 라벨)**.
2. **드론 영상 프레임은 클립 단위로 분할한다.** 프레임 단위 무작위 분할은 누수 →
   지표 부풀려짐. 분할 후 split 간 공유 클립 0 을 assert.

Roboflow 데이터에도 같은 주의가 필요하다. 같은 장면의 연속 프레임이 섞여 있는 경우가
많아, **파일명·해시 기준으로 근접 중복을 확인**한 뒤 분할한다.

하이퍼파라미터는 `Yolo26/CLAUDE.md` 에 기록된 v1.0.1 sweep 최적값을 그대로 쓴다.
`imgsz=1024` 는 기존 `det-best.pt` 와 동일하게 **확정**했다 (2026-08-25).
sweep 최적값이 1024 기준이고, 기존 모델과 직접 비교가 가능하다는 이점이 있다.

다만 헬멧은 이 해상도에서 10~30 px 다. **헬멧 재현율이 목표에 못 미치면
해상도 상향 전에 아래 순서로 먼저 시도**한다 (재학습 비용이 낮은 순).

1. **추론 해상도 상향 (재학습 불필요)** ← 다인승에서 가장 효과가 컸다
2. 헬멧 클래스 전용 conf 임계 하향 (재학습 불필요)
3. 타일링 추론 — 프레임을 나눠 넣어 실질 해상도를 올린다 (재학습 불필요)
4. 드론 뷰 헬멧 라벨 보강 후 재학습 (같은 imgsz)
5. `imgsz=1280` 재학습

**1번을 맨 위로 올린 근거 (2026-08-27, 04 문서 7~9장).** 다인승 판정에서 미탐의 주
원인이 알고리즘이 아니라 **추론 해상도**였다. 학습은 1024 그대로 두고 **추론만**
1024 → 1536 으로 올리자 확정이 75 → 153 건으로 2배가 되었다. 드론 뷰에서 사람 박스가
추론 입력 기준 16~40 px 로 작기 때문이며, **헬멧은 그보다 더 작으므로 같은 문제가
더 심하게 나타날 것으로 본다.** 학습 imgsz 1024 결정은 그대로 유지한다 — 바꾼 것은
추론 해상도뿐이다.

**클래스 추가(`no_helmet`)는 이 목록에 없다.** 4장에서 미도입으로 확정했다.

### 사전 가중치

`det-best.pt` 를 초기값으로 쓸 수 있으면 4클래스 학습분을 재활용해 수렴이 빠르다.
다만 클래스 수가 4→5 로 바뀌어 **탐지 헤드의 출력 채널이 달라진다.** Ultralytics 는
불일치 레이어를 건너뛰고 로드하므로 백본·넥은 승계된다.
→ **스크래치 학습과 `det-best.pt` 승계 학습 2회를 돌려 비교**한다.

### 평가 기준

- 클래스별 P/R/mAP50/mAP50-95 를 **전 클래스 행으로** 기록한다 (all 만 보기 금지).
- **`helmet` 의 재현율이 최우선 지표다.** 5클래스 스키마에서는 헬멧 미탐이 곧
  "미착용" 오탐이 되기 때문이다 (4장 ①). 재현율 0.9 는 착용자 10명 중 1명을

## 9. 후처리 — 연관과 판정

모델 출력(박스들)에서 위반을 뽑아내는 규칙이다.

구현 위치는 `src/event_detection/` 로 계획했으나, 이 저장소의 `src/` 가 비어 있고 실행
스크립트가 전부 `scripts/05-오토바이헬멧및다인승/` 에 있어 **현행 구조를 따라 거기에 두었다**
(`detect_motorcycle_multi_rider.py`). `src/` 모듈화는 v5.3.1 과 함께 별도로 다룬다.

### 9.1 라이더 연관

```text
for each motorcycle M:
    riders(M) = { person P : overlap(P, M) 조건 만족 }
```

드론 하향 뷰에서는 사람이 오토바이 **위에 겹쳐** 보이므로 판정식은 IoU 가 아니라
**포함비**가 적절하다.

```text
overlap(P, M) = area(P ∩ M) / area(P)   ≥ τ     (τ 는 실측으로 결정)
```

IoU 를 쓰면 사람 박스가 오토바이보다 작아 값이 낮게 나와 연관이 끊긴다.

**실측 결과 (2026-08-25):** τ = 0.30 으로 구현했으나 **이 조건만으로는 오토바이 옆에 선
보행자가 탑승자로 잡힌다.** 그래서 조건을 하나 더 걸었다.

```text
탑승자 조건 = overlap(P, M) ≥ τ  그리고  center(P) 가 M 박스 안
```

탑승자는 오토바이 위에 앉아 있어 몸통 중심이 박스 안에 떨어진다. 여유분은 **0** 이어야
한다 — 0.05 만 줘도 실측된 보행자 사례가 통과한다. 상세는 04 문서 3.2.

또한 **사람 1명은 가장 많이 겹치는 오토바이 1대에만 배정한다.** 여러 대에 중복
배정하면 한 사람 때문에 두 대가 동시에 다인승으로 오탐된다.

### 9.2 다인승 판정

```text
|riders(M)| ≥ 2  →  다인승 위반 후보
```

**주의점 ①: 두 사람이 한 박스로 합쳐짐 (미탐 방향).** 드론 뷰에서 앞뒤로 탄 두 사람은
박스가 크게 겹친다. NMS 가 둘 중 하나를 지워버릴 수 있다.

**실측 결과 이 현상은 관측되지 않았다.** `--nms-iou` 를 0.70 → 0.90 → 0.95 로 올려도
확정·후보 건수가 한 건도 변하지 않았다 (162756: 17/483 고정, 164800: 9/205 고정).
NMS 가 탑승자를 지우고 있지 않다는 뜻이다. 04 문서 3.1.1 ④.

**주의점 ②: 한 사람이 두 박스로 잡힘 (오탐 방향) — 실측으로 확인된 주 오탐 원인이다.**
상반신만 잡힌 작은 박스가 전신 박스 **안에 들어앉으면** IoU 가 낮아 NMS 를 통과한다.
드론 영상 5개(31,758프레임) 기준으로 이 필터를 끄면 **확정이 75건 → 127건으로
1.7배 부풀어 오른다.** 늘어난 52건은 전부 1인 탑승 오탐이다.

→ NMS 뒤에 `inter / min(area) ≥ 0.75` 기준으로 한 번 더 거른다. 상세는 04 문서 3.1.

**반대 방향(미탐)도 확인했다.** 병합 3,540건 전수 조사에서 91.8% 가 겹침 0.85 이상
(사실상 한 박스가 다른 박스 안에)이었고, 의심 구간 56건(1.58%) 중 표본 8건을 확대
검토한 결과 진짜 2인을 합친 사례는 나오지 않았다 (04 문서 3.1.1). 다만 정답 라벨과의
대조가 아니므로 "미탐 0" 이라고 단정하지는 않는다.

①과 ②는 방향이 반대다. `--nms-iou` 를 올리면 ①은 줄지만 ②는 늘어난다.
**②는 NMS 임계로 풀지 말고 위 포함비 필터로 푼다.**

### 9.3 헬멧 미착용 판정 (5클래스)

**판정 대상은 9.1 에서 오토바이와 연관된 사람 `riders(M)` 뿐이다.** 연관되지 않은
사람(보행자 등)은 헬멧이 없어도 위반이 아니며, 아예 순회 대상에 들어가지 않는다.

`no_helmet` 클래스가 없으므로 **helmet 박스의 부재**로 판정한다. 그래서 판정을
그대로 쓰지 않고 **보류 조건을 먼저 건다.**

```text
for each rider P in riders(M):      # ← 오토바이 탑승자만. 보행자는 제외
    # ① 판정 가능 여부부터 확인
    if area(P) < A_min            →  판정 불가 (너무 작아 헬멧을 볼 수 없음)
    if P 가 화면 경계에 걸림       →  판정 불가
    if P 가 다른 객체에 크게 가려짐 →  판정 불가

    # ② 머리 영역 = 사람 박스 상단 일부
    head_zone(P) = P 의 상단 h_ratio 구간

    # ③ 헬멧 유무
    if ∃ helmet 박스 H : center(H) ∈ head_zone(P)  →  착용
    else                                            →  미착용 후보
```

- `A_min`, `h_ratio` 는 드론 고도에 따라 달라지므로 **test 셋 실측으로 결정**한다.
- 헬멧 클래스는 **다른 클래스보다 낮은 conf 임계**를 쓴다 (예: 전체 0.25, helmet 0.15).
  미탐 1건이 오탐 1건이 되는 구조라, 헬멧은 조금 과하게 잡는 편이 안전하다.
- **"미착용 후보"는 아직 위반이 아니다.** 9.4 의 연속 프레임 조건을 통과해야 확정된다.

### 9.4 트래킹으로 안정화

단일 프레임 판정은 흔들린다. 5클래스 스키마에서는 이 단계가 **선택이 아니라 필수**다.
헬멧이 한 프레임 깜빡 안 잡히는 것만으로 위반이 만들어지기 때문이다.

기존 파이프라인의 트래커를 이용해 트랙 단위로 누적한다.

```text
트랙 T 의 최근 W 프레임 중
   미착용 후보 비율 ≥ r   →  미착용 위반 확정
   그 외                   →  미확정 (유지)
```

`W`(윈도우), `r`(비율)은 실측으로 결정한다. 단순 "N 프레임 연속" 보다 비율 방식이
간헐적 미검출에 강하다.

**다인승 구현값 (2026-08-25):** `W=15`, `r=0.6`, 최소 관측 8 프레임. 확정된 트랙은
이후 계속 위반으로 유지한다. **트랙 ID 가 붙지 않은 오토바이는 확정하지 않고** 후보로만
세어 별도 집계한다 — 시간 누적을 할 수 없기 때문이다.

트래킹은 `src/tracking/` 이 아니라 Ultralytics `bytetrack.yaml` 을 그대로 쓴다
(v5.3.1 릴리스와 동일). `botsort.yaml` 은 optical flow GMC 때문에 쓰지 않는다.

## 12. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **부분 라벨 오염** | 클래스 재현율 붕괴, 학습 중엔 안 보임 | 6.3 병합 규칙 + 6.4 결손 처리 + 8단계 vis 검수 |
| **도메인 갭** (지상 → 드론) | 헬멧 클래스만 성능 미달 | 드론 뷰 데이터 필수 확보, val/test 는 드론 뷰 전용 |
| **헬멧 미탐 → 미착용 오탐** | 착용자를 위반자로 신고. 5클래스 구조상 가장 큰 위험 | 헬멧 전용 낮은 conf + 판정 보류 + 연속 프레임 확정 (9.3~9.4). 그래도 부족하면 **드론 뷰 헬멧 라벨 보강** (클래스 추가는 하지 않음) |
| **연관 실패로 판정 누락** | 오토바이 탑승자를 못 이으면 헬멧 위반도 못 잡는다 | 9.1 포함비 임계 τ 를 test 셋 실측으로 결정, 연관 실패 사례를 별도 계수 |
| **헬멧 크기 부족** (1024 에서 10~30 px) | helmet 재현율 저하 | ① conf 하향 → ② 타일링 추론 → ③ imgsz 1280 재학습 (8장 순서) |
| **2인 박스 병합** | 다인승 미탐 | NMS iou 조정, test 셋에서 병합 사례 계수 |
| **한 사람이 두 박스로 분할** (실측 확인) | 1인 탑승이 다인승으로 오탐. NMS 를 통과해 조용히 발생 | `inter/min(area) ≥ 0.75` 로 재필터 (9.2 주의점 ②). 적용 후 34건 → 0건 |
| **밀집 구간 오연관** (실측 확인) | 정체 시 옆 차선 라이더가 탑승자로 계수. 혼잡도가 곧 오탐률 | 미해결. τ 상향 / 비율 r 상향 / 움직임 일치 조건 중 선택 필요 (04 문서 5장) |
| **클래스 ID 밀림** | 전 클래스 오염 | 리맵 후 vis 30장 확인 (규칙상 필수) |
| **split 누수** | 지표 과대평가 | 클립 단위 분할 + 공유 클립 0 assert |
