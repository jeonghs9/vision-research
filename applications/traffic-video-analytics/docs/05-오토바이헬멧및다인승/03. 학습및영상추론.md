## 3. 학습이 진행될수록 실영상 성능이 나빠진다

사용자가 실제 영상에서 **초기 에폭이 더 좋았다**고 관찰했다. 수치로도 방향이 일치한다.

| 가중치 | 오토바이 대비 헬멧 비율 |
|---|---:|
| ~epoch 65 (164259 전체 영상) | **16.0%** |
| epoch 189 (164259 일부 클립) | **2.4%** |

> 구간이 달라 직접 비교는 아니다. 같은 클립·같은 설정의 대조는 002 의 `epoch50.pt` 확보 후 수행한다.

### 통상적인 과적합이 아니다

1장 표에서 보듯 **val 손실이 끝까지 내려간다.** 과적합이면 반등해야 한다.

원인은 **도메인 갭**으로 보인다. val 472장은 Vehicle v3 의 고각 CCTV 이미지이고,
테스트 영상은 실제 드론 촬영이다. 학습이 진행될수록 모델이 학습 데이터 분포에
특화되면서, 그 분포에서 벗어난 실제 드론 영상에서는 오히려 나빠질 수 있다.

**이 현상은 현재 val 지표로는 잡히지 않는다.** 02 문서 6.5 에서 우려한 도메인 갭이
이렇게 드러난 것으로 보이며, 실제 드론 프레임을 val 에 넣어야 해결되는 문제다.

## 4. 002 재학습 — 초기 에폭 가중치 확보

Ultralytics 는 기본적으로 `best.pt` / `last.pt` 두 개만 저장하고 계속 덮어쓴다
(`save_period: -1`). **001 의 50 에폭 가중치는 남아 있지 않다.**

| 항목 | 값 |
|---|---|
| 실행 | `002-helmet-5cls-ep50repro` · 2026-08-27 18:39 시작 |
| GPU | **0,1,2** (001 은 3~7 에서 계속 진행) |
| batch | **39** (GPU 3장 × 13) |
| epochs | **500 유지** ← 001 과 학습률 곡선을 맞추기 위함 |
| save_period | **10** — `epoch10.pt` … 가 순차 저장된다 |
| 예상 | 에폭당 약 26분 · 50 에폭까지 약 21시간 |

### `epochs=500` 을 유지한 이유

`epochs=50` 으로 바꾸면 **학습률 스케줄이 달라진다.** `lrf=0.1101` 감쇠가 총 에폭에
걸쳐 일어나므로, `epochs=50` 은 50 에폭에서 학습률이 최저점에 도달하고
`epochs=500` 은 아직 높다. 001 의 50 에폭 지점을 재현하려면 500 을 유지해야 한다.

### batch 를 40 → 39 로 바꾼 이유

`trainer.py:323` 에서 `batch_size = self.batch_size // world_size` 로 나눈다.
GPU 3장에 `batch=40` 을 주면 40÷3=13 으로 **내림되어 실제 총 배치가 39가 된다.**
에러 없이 조용히 달라지므로 39로 명시했다. 001 의 완전한 재현은 아니다.

## 5. 운영 중 확인한 것

| 항목 | 내용 |
|---|---|
| **`nohup` + 환경변수** | `nohup PYTHONNOUSERSITE=1 yolo ...` 는 nohup 이 환경변수를 명령어로 해석해 **실패한다.** `nohup env PYTHONNOUSERSITE=1 ...` 으로 `env` 를 끼워야 한다 |
| **`GITHUB_ACTIONS=1` 의 대가** | Ultralytics 의 `_should_update()` 가 항상 False 를 반환해 **에폭 도중 로그가 완전히 침묵한다.** 로그 파일은 깨끗해지지만 실시간 확인은 불가능하다. 실시간을 원하면 이 변수를 빼야 하며, 로그는 에폭당 약 2 MB 로 늘어난다 |
| **실행 디렉터리에 파일을 두지 말 것** | Ultralytics 가 실행 디렉터리를 정리하면서 안에 둔 파일을 지운다 (`config.yaml` 이 삭제됐다). 기록과 로그는 상위 폴더에 둔다 |
| **`best.pt` 스냅샷** | 학습 중 계속 덮어써지므로, 비교용 추론 전에 `snapshots/001_best_ep189.pt` 처럼 복사본을 남긴다. 그래야 "이 영상은 어느 시점 모델인지"가 고정된다 |
| **페이지 캐시** | 데이터셋 전체가 RAM 에 캐시되어 `/proc/<pid>/io` 로는 진행률을 추정할 수 없다 (읽기량 4.6 MiB) |
