## 1. 왜 하는가

06 문서의 결론은 **어떤 평가 셋도 실영상 성능을 대변하지 못한다**였다.
val/test 가 학습과 같은 도메인(Vehicle v3, 고각 CCTV)이라 지표가 계속 올라가는데
실제 드론 영상에서는 헬멧 검출이 98 % 사라졌다.

근본 대책은 **실제 배포 대상 영상을 학습·평가에 넣는 것**이다.
이 문서는 그 실행 기록이다.

동시에 **head 클래스를 새로 도입**한다. 5클래스 스키마는 "helmet 박스가 없으면 미착용"
이라는 부재 추론이라 헬멧 미탐이 곧 오탐이 됐다. head 를 직접 탐지하면 판정이 명시적이 된다.

### `-ss` 점프를 쓰면 안 된다

처음 랜덤 프레임 10장을 `-ss` 로 뽑았더니 **전부 회색 화면**이었다
(평균 RGB 128, 표준편차 0.6~3.9). 이 `.ts` 파일들은 참조 프레임이 깨져 있어
(`Could not find ref with POC`) 키프레임 점프 시 디코딩에 실패한다.

```bash
# 잘못 — 회색 프레임이 나온다
ffmpeg -ss 65.76 -i input.ts -frames:v 1 out.jpg

# 올바름 — select 필터로 순차 디코딩
ffmpeg -nostdin -i input.ts -vf "select='not(mod(n\,5))'" -vsync 0 -q:v 2 out_%06d.jpg
```

`-nostdin` 도 필요하다. 없으면 ffmpeg 가 stdin 을 소비해 `while read` 루프가 첫 줄만 처리하고 끊긴다.

전수 검사(6,364장)로 회색 13장을 찾아 `excluded/` 로 옮겼다. 전부 각 영상 맨 앞 1~5장이다.

## 3. SAM3 입력 해상도 — 1008 고정이다

`sam3_image_processor.py:19`

```python
def __init__(self, model, resolution=1008, ...):
    v2.Resize(size=(resolution, resolution))   # 정사각형 강제, 종횡비 무시
```

`resolution` 은 생성자 인자지만 **바꾸면 실패한다.** RoPE 텐서가 1008 기준으로
미리 계산돼 있어 `vitdet.py:65` 에서 assert 로 막힌다.

```text
assert freqs_cis.shape == (x.shape[-2], x.shape[-1])   # AssertionError
```

1512 · 2016 · 2880 모두 같은 지점에서 실패했다.
`vitdet.py` 에 position embedding interpolate 코드가 있으나 그 경로는 활성화되지 않는다.

### 그래서 타일 분할이 유일한 방법이다

1008 리사이즈가 헬멧 크기에 미치는 영향:

| 그룹 | 원본 | 가로 축소 | 세로 축소 | 20px 헬멧 → |
|---|---|---:|---:|---|
| 드론 | 2880×1620 | 2.86× | 1.61× | 7.0 × 12.4px |
| 4K | 3840×2160 | 3.81× | 2.14× | **5.2 × 9.3px** |

실측 (동일 4장):

| 설정 | 드론 helmet | 4K helmet | 초/장 | VRAM |
|---|---:|---:|---:|---:|
| 통짜 (res1008) | 77 | **1** | 1.9 | 5.9G |
| tile 2×2 | 146 | 27 | 4.8 | 4.7G |
| **tile 3×3** | **188** | **57** | 10.4 | 4.6G |

4K 에서 1개 → 57개다. 초기에 "고속도로라 오토바이가 적어서" 라고 추측했으나
헬멧이 5픽셀로 뭉개져 안 보였던 것이다. **tile 3×3 채택.**

## 5. 오탐 필터 — 사용자 지적 2건에서 나왔다

시각화 검수에서 두 문제가 지적됐고, 정량화 후 필터를 설계했다.

### 지적 ① "오토바이 안에 작은 오토바이가 또 잡힌다"

| 클래스 | 총 | 큰 박스에 잠긴 것 | 비율 |
|---|---:|---:|---:|
| person | 781 | 134 | 17.2 % |
| car | 216 | 40 | 18.5 % |
| motorcycle | 706 | 82 | 11.6 % |
| helmet | 378 | 9 | 2.4 % |

### 지적 ② "사람인지 헬멧인지 길쭉하게 잡힌다"

정상 범위는 helmet 0.77~1.58, head 0.65~1.29 인데 극단값이 있었다.

```text
helmet  93.9px  w/h 0.10   score 0.83
head    99.8px  w/h 0.10
head    49.1px  w/h 6.68
```

### 최종 필터

| # | 필터 | 대상 | 기준 |
|---|---|---|---|
| ① | 종횡비 | helmet · head | w/h 0.5~2.0 밖 제거 |
| ② | 중첩 | car · motorcycle | IoS ≥ 0.8 **그리고 면적비 < 0.5** |
| — | ~~중첩~~ | ~~person~~ | **미적용** (아래 참조) |
| ③ | 사람 연관 | helmet · head | person 과 50 % 미만 겹치면 제거 |
| ④ | head−helmet | head | helmet 과 IoU ≥ 0.4 제거 |

**②의 면적비 조건이 핵심이다.** 단순히 "안에 들어있으면 제거" 가 아니라
"안에 들어있고 크기가 절반 미만" 일 때만 지운다. 크기가 비슷하면 겹쳐 선 차량이므로 살린다.

### person 에 중첩 필터를 걸면 2인 탑승이 지워진다

사용자가 "사람은 2인 탑승인 경우도 지워버리는 것 같다" 고 지적해 검증한 결과다.

| 설정 | 2명 이상 오토바이 | 보존율 |
|---|---:|---:|
| 필터 없음 | 52대 | — |
| v1 person IoS 0.8 | 29대 | **56 %** |
| v2 person 완화 (IoS 0.95, 면적비 0.15) | 44대 | 85 % |
| **v3 person 제외** | **50대** | **96 %** |

앞뒤로 탄 두 사람은 박스가 IoS 0.95~1.00 으로 겹치고, 뒷사람이 가려져 작게 잡힌다.
**v1 은 52건 중 21건(44 %)을 지우고 있었다.** 다인승 판정이 목적이므로 v3 를 채택한다.
군중 박스 오탐이 일부 남지만, 다인승 후처리(04 문서)가 이미 군중 필터를 갖고 있다.

## 7. 학습 실험 A · B · C

**데이터를 어떻게 구성할지**를 논쟁 대신 실험으로 정한다.

| | **A 단순병합** | **B 2단계 파인튜닝** | **C 드론 단독** |
|---|---|---|---|
| 초기 가중치 | 스크래치 (yaml) | **`det-best.pt`** | 스크래치 (yaml) |
| 학습 데이터 | COCO 62,898 + 드론 4,505 | 드론 4,505 | 드론 4,505 |
| GPU | 0–3 (DDP) | **4 (단일)** | **5 (단일)** |
| **batch** | **40** | **4** | **4** |
| epochs | 60 | 150 | 150 |
| lr0 / lrf | 0.009906 / 0.1101 | **0.001 / 0.01** | 0.009906 / 0.1101 |
| warmup_epochs | 0.4234 | **1.0** | 0.4234 |
| patience | 20 | 30 | 30 |
| 에폭당 | 약 17분 | 약 4분 | 약 4분 |
| 예상 | 약 17시간 | 약 10시간 | 약 10시간 |

B·C 는 원래 GPU 4장 DDP · batch 40 계획이었으나 **데드락으로 단일 GPU batch 4 로 바꿨다** (11장).
덕분에 순차 실행 계획이 **동시 실행**으로 바뀌어 시간이 절약됐다.

**batch 가 A(40) 와 B·C(4) 로 다르다.** 드론 데이터는 객체 밀도가 COCO 의 40배라
큰 배치를 쓸 수 없다. 비교 시 이 차이를 감안해야 한다.

- **A vs B** — 병합이 나은가, 파인튜닝이 나은가
- **B vs C** — COCO 사전학습이 실제로 도움이 되는가 (batch·epochs 동일, 초기값만 다름)
- **A vs C** — 데이터 구성만의 효과

B 의 학습률을 낮춘 이유는, 스크래치와 같은 lr 을 쓰면 `det-best.pt` 가 COCO 에서 배운 것을
초반에 지워버려 사전학습 의미가 사라지기 때문이다.

### 공통 평가 — 영상 단위 홀드아웃

```text
train  162756 · 163257 · 164259   4,505장
val    163758                     1,504장   ← best.pt 선택 기준
test   164800                       342장   ← 최종 평가
```

**영상 단위로 나눈다.** 같은 영상에서 프레임을 무작위로 나누면 인접 프레임(0.2초 차이)이
train 과 test 에 흩어져 지표가 부풀려진다 (02 문서의 augmentation 누수와 같은 원리).

val 도 영상 단위로 분리해 `best.pt` 가 **처음 보는 영상 기준**으로 선택된다.
001 에서 겪은 "val 이 학습과 같은 도메인" 문제를 구조적으로 막는다.

### OOM 자동 재시도

```bash
BATCHES="40 32 24 16 8"
```

OOM 감지 시 DDP 정리 → 30초 대기 → 실행 디렉터리 삭제 → 다음 batch 로 재시도.
**GPU 수로 나누어떨어지는 값만** 쓴다 (`trainer.py:323` 이 `batch // world_size` 로 나눈다).
OOM 이 아닌 오류는 재시도하지 않고 중단한다.

사용된 batch 는 `<실험명>.batch` 파일에 기록된다.

| 12:00 | **1시간 29분 무응답.** rank 3개 `Rsl` CPU 99.9 % busy-wait, 1개 `futex_wait`. `weights/` 비어 있음 |

### 원인

**① 객체 밀도.** 드론 프레임은 장당 217개, COCO 는 4~5개다.

`TaskAlignedAssigner` 는 `(batch, anchors, max_objects)` 텐서를 만든다.
imgsz 1024 → 앵커 21,504개.

```text
batch 40 × 21,504 앵커 × 5,000 객체 = 4.3억 원소
```

**② Ultralytics 는 죽지 않고 CPU 로 폴백한다.** 단독 실행이면 느려질 뿐이지만 DDP 에서는 다르다.

**③ DDP 는 모든 rank 가 같은 연산을 같은 순서로 수행하는 것을 전제한다.**
그런데 OOM 폴백은 **rank 마다 독립적으로** 일어난다. GPU 4 는 CPU 로, GPU 5 는 GPU 로 가면
실행 경로가 갈리고, `all_reduce` 같은 집합 통신에서 서로를 영원히 기다린다.
검증 직후 지표 동기화 지점에서 멈춘 것이 이 때문이다.

**A 는 멀쩡했다** — COCO 가 섞여 배치당 376개라 OOM 이 0회였고, 따라서 폴백도 rank 분기도 없다.

### 시도 이력

| # | 구성 | GPU당 이미지 | 배치당 인스턴스 | 결과 |
|---|---|---:|---:|---|
| 1 | DDP 4장 · batch 40 | 10 | 3,951 | OOM 14회 → **데드락** |
| 2 | DDP 4장 · batch 16 | 4 | 1,404 | OOM 0회지만 **검증 후 데드락** |
| 3 | 단일 · batch 16 | **16** | ~5,700 | OOM 재발, **209초/it** |
| 4 | **단일 · batch 4** | **4** | ~1,400 | **OOM 0회 · 4.8 it/s** ✅ |

3번은 실수였다. DDP 의 `batch=16` 은 **GPU당 4장**인데, 단일 GPU 로 옮기며 같은 숫자를 써서
**GPU당 16장**이 되어 4배 부하가 됐다. `trainer.py:323` 이 `batch // world_size` 로 나눈다.

### 교훈

- **객체가 많은 데이터셋은 batch 를 GPU당 4장 수준으로 제한한다.** 메모리 여유(14 GB 사용)와
  무관하게 assigner 텐서가 터진다.
- **OOM 폴백 경고를 무시하면 안 된다.** 크래시가 아니라 WARNING 이라 재시도 로직이 잡지 못했다.
  로그에 `TaskAlignedAssigner` 가 보이면 batch 를 줄여야 한다.
- **DDP 를 쓸 수 없는 상황이 있다.** 데이터가 작으면(4,505장) 단일 GPU 로 여러 실험을
  동시에 돌리는 편이 낫다.
