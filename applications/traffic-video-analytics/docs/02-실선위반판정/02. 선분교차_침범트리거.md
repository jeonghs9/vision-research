## 1. 왜 또 바꿨나 — pin 방식의 근본 질문

05번 문서의 "고정(pin)+비율" 방식은 오탐을 많이 줄였지만, 사용자가 근본적인
질문을 던졌다: **"왜 굳이 가장 가까운 선을 찾아서 고정해야 하지? 그냥 화면에
보이는 선이 차량 밑변과 맞닿으면서 반대편으로 다 넘어가면 발화하면 안 되나?"**

맞는 지적이었다 — "고정"은 "매 프레임 선을 다시 찾으면 엉뚱한 선으로 튈 수
있다"는 문제를 막기 위한 장치였는데, 애초에 **"실제로 맞닿아 있는 선만
본다"**면 그 문제 자체가 생길 수가 없다. 멀리 있는 무관한 선은 맞닿을 수
없기 때문이다.

## 2. 시행착오 — "거리 없이 순수 기하학"이 처음엔 두 번 깨짐

### 2.1 즉시발화 버전 — 오탐 폭증 (실패, 폐기)

처음엔 "밑변 양 끝점의 부호가 실선 기준으로 다르면(걸쳐있으면) → 반대편으로
완전히 넘어가는 순간 즉시 발화"로 만들었다. 결과: YOLO-pose 78건, GANet
49건 발화 — 완전히 실패. 원인: **거리 제한이 아예 없어서**, 매 프레임
"아무 실선이나" 잠깐 걸치는 것처럼 계산되면 바로 발화해버렸다. 이 버전은
삭제했다.

### 2.2 1.5초 유지 추가 — 그래도 한 건 남음 (#9328)

v5.3.1 방식처럼 "완전히 넘어간 상태가 1.5초 유지돼야 발화"를 추가하니
오탐이 크게 줄었다(YOLO-pose 2→1건 발화, 전부 정답). 그런데 GANet에서
`#9328`이 **1.5초(45프레임)를 꽉 채우고도** 발화했다 — 로그를 보니 전혀
흔들림 없이 깨끗하게 45프레임 내내 "반대편"으로 나왔다. 노이즈가 아니라
**일관되게 틀린 경우**였다.

**좌표를 직접 찍어서 확인**(진단 스크립트로 해당 구간 실선 좌표 + 차량 박스
위치를 그려봄)한 결과: 실선과 차량이 화면에서 **1000px 넘게 떨어진, 완전히
무관한 위치**에 있었다. 원인은 `point_to_polyline_signed_distance`가
**무한 직선 기준으로 부호만 비교**하지, 거리가 말이 되는지는 전혀 안
본다는 것 — 아무리 멀어도 수학적으로는 "왼쪽/오른쪽"이 계산된다. 차량의
왼쪽 끝점과 오른쪽 끝점이 그 먼 선 기준으로 우연히 "부호가 다르게" 나오면
"걸쳐있다"로 오판했다.

## 3. 최종 해결 — 무한 직선 부호 비교 → 진짜 유한 선분 교차 검사

"걸쳐있다"의 정의를 **"두 선분이 실제로(유한한 구간 안에서) 교차하는가"**로
바꿨다 — 표준 방향(orientation) 기반 선분 교차 판정이다. 이러면 **거리
제한을 따로 안 둬도** 실제로 안 닿아있는 선은 애초에 교차할 수 없다.

```python
def _segments_cross(p1, p2, p3, p4) -> bool:
    """선분 p1-p2 와 p3-p4 가 (무한 직선이 아니라) 유한한 구간 안에서
    실제로 교차하는지. 표준 방향(orientation) 기반 판정."""
    def cross(o, a, b):
        return (a[0]-o[0])*(b[1]-o[1]) - (a[1]-o[1])*(b[0]-o[0])
    d1 = cross(p3, p4, p1); d2 = cross(p3, p4, p2)
    d3 = cross(p1, p2, p3); d4 = cross(p1, p2, p4)
    return ((d1 > 0) != (d2 > 0)) and ((d3 > 0) != (d4 > 0))

def bottom_edge_touches_polyline(p_left, p_right, polyline) -> bool:
    for i in range(len(polyline) - 1):
        if _segments_cross(p_left, p_right, polyline[i], polyline[i + 1]):
            return True
    return False
```

이 교차 검사를 **"교차 시작" 판정의 게이트**로 추가했다(기존 "부호가
다르다" 체크는 유지하되, 그 전에 반드시 실제 교차가 확인돼야 통과). 이걸
적용하자 `#9328`이 완전히 사라졌다(재검증 완료).

## 4. 최종 판정 로직 — "에피소드" 방식

pin도, 거리 제한도, 차로폭(bracket/비율) 계산도 전부 없앴다. 차량마다 아래
상태만 추적한다:

1. **평소**: 아무 선도 추적 안 함(에피소드 없음)
2. **교차 시작**: 어떤 실선이든 밑변 선분과 실제로(유한 범위 내) 교차하기
   시작하면, **그 순간 직전 프레임**의 밑변 위치로 "원래 있던 쪽"
   (`before_sign`)을 역산해서 에피소드를 연다
3. **진행 중**: 매 프레임 그 선 기준 부호를 다시 확인
   - 아직 걸쳐있음(교차 중, 부호 불확정) → 계속 대기
   - `before_sign`과 같은 쪽으로 돌아옴 → 에피소드 취소(스쳤을 뿐)
   - 완전히 반대쪽 → **그 상태가 `--hold-seconds`(1.5초) 유지**돼야 발화
     (1프레임만 반대쪽이어도 바로 발화하면 또 노이즈에 당함)
4. 그 선의 트랙이 사라지면 에피소드 취소

한 번에 한 차량당 최대 1개의 에피소드만 연다. 기준이 되는 선(tid)이
바뀌는 게 아니라 **애초에 "실제로 닿은 선"만 다루므로**, 05번 문서에서
고민했던 "기준선이 여러 개면 뭘 기준으로 할지" 문제 자체가 안 생긴다.

## 5. 화면 표시

매 프레임 추적 중인 모든 차선을 상시 표시한다 — **실선=초록, 점선=노랑**.
(처음엔 "교차 중"인 선만 자홍색으로 강조했는데, 상시 표시를 추가한 뒤로는
불필요해서 뺐다.) 각 차량의 밑변은 하늘색으로 표시, 박스는 평소=노랑,
교차 중=주황, 위반 확정=빨강+"VIOLATION".

영상 저장은 `cv2.VideoWriter(mp4v)` 대신 **ffmpeg(libx264)에 raw 프레임을
파이프로 직접 흘려서** 처음부터 압축된 h264로 저장한다 — mp4v는 거의 압축이
안 돼서 5분 영상이 1.9GB까지 나왔는데, 이 방식은 500MB 이하로 끝난다(끝나고
따로 재인코딩할 필요도 없음).

```python
class FfmpegWriter:
    def __init__(self, out_path, w, h, fps, crf=23, preset="fast"):
        cmd = ["ffmpeg", "-y", "-f", "rawvideo", "-pix_fmt", "bgr24",
               "-s", f"{w}x{h}", "-r", str(fps), "-i", "-",
               "-c:v", "libx264", "-crf", str(crf), "-preset", preset,
               "-pix_fmt", "yuv420p", out_path]
        self.proc = subprocess.Popen(cmd, stdin=subprocess.PIPE, ...)
    def write(self, frame): self.proc.stdin.write(frame.tobytes())
    def release(self): self.proc.stdin.close(); self.proc.wait()
```
