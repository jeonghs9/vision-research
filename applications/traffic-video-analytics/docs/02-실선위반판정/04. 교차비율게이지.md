## 1. 계기 — "IoU/IoA처럼 연속값으로 보면 안 되나?"

07번 문서까지의 발화 로직은 전부 **이산적**이다 — 밑변 양 끝점이 실선
기준으로 "같은 쪽"(sign 확정) 아니면 "걸쳐있음"(sign=None) 둘 중 하나로만
판단한다. 사용자가 "차로변경 위반 차량은 차량 밑변선분이랑 실선이랑
점점 IoU나 IoA가 증가할 거 아니냐"고 제안 — 밑변이 실제로는 몇 %나
넘어갔는지 연속값으로 보면, 진짜 침범(완만하게 0→100%)과 ID 재할당 오탐
(순간적으로 0%→100% 점프)을 구분하는 새 신호가 될 수 있다는 아이디어.

**방침**: 발화 로직을 바로 바꾸지 않고, 먼저 ratio를 계산·로깅·시각화만
해서 실제 정탐/오탐 사례에서 어떤 패턴이 나오는지 관찰하기로 함.

## 2. `crossing_ratio()` 설계

```python
def crossing_ratio(p_left, p_right, polyline, before_sign) -> float:
    """밑변 선분이 "원래 쪽"(before_sign) 기준으로 몇 %나 반대편으로
    넘어갔는지 0~1 연속값으로 반환. 두 끝점이 같은 쪽이면 0(원래 쪽) 또는
    1(완전히 반대편). 걸쳐있으면, 두 끝점의 수직거리 비율로 교차점 위치를
    선형보간(닮은꼴 삼각형 — 국소적으로 선이 직선에 가깝다고 가정, 근사치)
    해서 "원래 쪽 끝점~교차점" 대 "교차점~반대쪽 끝점" 비율로 환산한다."""
```

- 에피소드가 활성 상태인 매 프레임마다 계산 → CSV `ratio` 컬럼에 기록.
- 영상에서는 박스 **밑변부터** 그 비율만큼 분홍색을 채워서 표시(색 농도가
  아니라 **채워지는 높이**로 진행도 표현 — 사용자가 명시적으로 요청한
  방식: "100%로 갈수록 진해지는 게 아니라 아래에서부터 점점 차오르는
  형태"). 확정(발화) 순간엔 기존 빨간 VIOLATION 박스로 전환.
- **발화 로직에는 전혀 관여하지 않는다** — `active_episode_by_car`/
  `flagged_cars`를 건드리는 분기는 손대지 않았고, ratio는 순수하게
  읽기 전용으로 계산·저장만 됨.

## 4. 사용자 질문으로 발견한 사각지대 — "뒤 트럭도 실선 밟고 있는데 왜 게이지가 안 뜨나?"

0816 영상 결과를 보던 사용자가, 화면에 같이 있던 두 트럭 중 앞 트럭은
분홍 게이지가 차오르는데 뒤 트럭(`#11191`)은 왜 안 뜨는지 질문.

**1차 답변은 틀렸다** — "점선을 밟고 있어서 그렇다"(실선 cls=0만 판정
대상이라서)고 답했으나, 디버그 로그로 실측해보니 둘 다 **같은 실선
(tid=119)을 touches=True로 밟고 있었다.** 추측으로 답하지 말고 실제
코드/데이터로 확인했어야 했는데 처음엔 그러지 못했다 — 사용자가 "다시
자세히 봐"라고 지적한 뒤에야 디버그 프린트를 코드에 임시로 삽입해서
재확인, 정정했다.

**진짜 원인**: `#11191`은 실선과 거의 나란히(사선으로) 달려서, 밑변이
"걸쳐있음"(`sign=None`) 상태가 frame 1631~1705+(75프레임, 2.5초+) 동안
연속됐다. 에피소드 시작 조건은:

```
1. 지금 이 프레임에서 sign이 None(걸쳐있음)
2. 직전 1프레임의 before_sign이 None이 아니어야(한쪽에 깔끔히 있었어야) 시작
```

"걸쳐있음"이 여러 프레임 지속되면 직전 프레임도 항상 `sign=None`이라
2번 조건에 매 프레임 걸려서 **에피소드가 영원히 시작되지 않는다** —
실선을 명백히 밟고 있어도 발화도 ratio 게이지도 전혀 안 뜬다.

## 5. 수정 시도 — 실패, 원복 (같은 날)

before_sign을 "직전 1프레임"이 아니라 **최근 hold_frames개(1.5초) 기록
중 마지막으로 sign이 확정됐던 프레임**까지 거슬러 찾도록 완화해서
구현(`box_history_by_car` 추가, 그 사이 진짜 탐지 공백이 있으면 기존과
동일한 1.5배 크기 가드도 적용). "시작 조건만 바뀌고 확정 안전장치는
그대로라 오탐 급증 리스크는 낮을 것"이라고 예상했으나 — **완전히
틀렸다.**

GANet 백엔드로 0816·1037·1539 전체 재검증한 결과, 발화 건수가 전부
폭증:

| 영상 | 수정 전 | 수정 후(실패) |
|---|---|---|
| 0816 | 1건 | **16건** |
| 1037 | 1건 | **17건** |
| 1539 | 1건 | **20건** |

원인을 신규 오탐(`#5174`, 0816) 실측으로 확인: 에피소드가 시작되는 **첫
프레임부터 이미 ratio=0.962**였다 — 추적 ID가 막 생긴 지 얼마 안 된
신규 트랙으로, 박스가 아직 안정되기 전 흔들리는 초기 몇 프레임 중 하나가
우연히 "한쪽에 깔끔히 있음"으로 잡혔고, lookback이 그걸 "원래 있던 쪽"
으로 오인해서 트랙이 생기자마자 바로 "거의 다 건너간" 상태로 에피소드가
열려버렸다.

즉 기존의 "직전 1프레임만 본다"는 엄격한 규칙은, 단순히 보수적인 설계가
아니라 **"막 생긴 불안정한 트랙"을 암묵적으로 걸러주는 역할을 겸하고
있었다** — lookback 범위를 넓히면서 이 암묵적 보호장치가 같이 풀려버린
것. 사용자가 시도 전에 "괜히 수정하면 오탐 늘어날 수도 있을 것 같다"고
우려했던 그대로였다.

**결론**: `crossing_trigger_bottomline_test.py`를 원본과 동일한 상태로
원복. 4절의 사각지대는 당분간 **의도적으로 미해결 상태**로 둔다.
재시도한다면 "최근 아무 프레임"이 아니라 "최근 K프레임 연속으로 같은
쪽에 안정적으로 있었던 경우"만 신뢰하는 식으로 훨씬 보수적으로 가야
할 것 — 미구현.

## 7. 파이프라인 구간별 처리속도

사용자 요청으로 `profile_stages.py`(1회성 프로파일링 스크립트, 발화
로직은 원본과 동일하고 구간별 시간 측정만 추가)를 만들어 GANet과
YOLO-pose 두 백엔드의 처리 속도를 비교했다. 0816 1분 클립(1800프레임,
GPU 단독 점유, 영상 출력 포함)으로 측정:

| 구간 | GANet (cache) | YOLO-pose (live) |
|---|---|---|
| 1. 차량탐지+추적 (YOLO det+ByteTrack, 디코딩 포함) | 37.1ms/f (23.9%) | 38.7ms/f (23.0%) |
| 2. 차량트래커 후처리 | 6.3ms/f (4.1%) | 8.1ms/f (4.8%) |
| 3. 에고모션 추정(ORB) | 86.0ms/f (55.5%) | 81.8ms/f (48.6%) |
| 4. 차선검출 | 0.1ms/f (0.1%) | 14.2ms/f (8.4%) |
| 5. 차선추적(LaneTracker) | 0.5ms/f (0.3%) | 0.4ms/f (0.2%) |
| 6. 판정로직(교차 상태머신) | 3.7ms/f (2.4%) | 3.2ms/f (1.9%) |
| 7. 그리기 | 9.9ms/f (6.4%) | 9.1ms/f (5.4%) |
| 8. 인코딩(ffmpeg) | 11.3ms/f (7.3%) | 12.8ms/f (7.6%) |
| **총 처리속도** | **6.45 fps** (155ms/f) | **5.94 fps** (168ms/f) |

**관찰**:
- **에고모션 추정(ORB 특징점 매칭)이 두 백엔드 모두 압도적 1위 병목
  (48~56%)** — 차량 탐지(23%)보다도 크다. 매 프레임 1500개 ORB
  특징점을 뽑고 BFMatcher로 직전 프레임과 매칭하는 과정이 전체
  파이프라인에서 가장 느리다.
- 두 백엔드의 차이는 거의 전적으로 **4. 차선검출** 구간에만 있다 —
  GANet은 미리 뽑아둔 캐시(JSONL 한 줄 읽기)라 0.1ms/f로 사실상
  공짜, YOLO-pose는 매 프레임 실제 포즈 모델을 돌려서 14.2ms/f.
  이 차이(약 14ms/f)가 거의 그대로 전체 처리속도 차이(6.45→5.94fps,
  약 8% 저하)로 이어진다.
- 판정로직(ratio 계산 포함)은 전체의 2% 안팍으로 무시할 만한 비중 —
  이번에 추가한 ratio/분홍 게이지 기능이 성능에 미치는 영향은 미미하다.
- 처리속도(5.9~6.5fps)는 원본 영상 fps(약 30fps)보다 훨씬 느려서
  **실시간 처리는 안 된다** — 현재는 오프라인 분석/검증용 스크립트로만
  사용 중이라는 점 참고(production 파이프라인은 별도).

## 9. 안전장치 2 교체 — "박스 크기 1.5배" → "교차 비율(ratio) 점프" (2026-10-16)

### 9.1 계기

07번 문서 3.3절의 박스-크기 가드는 1539의 오탐 3건을 전부 막아주지만,
**박스 크기가 비슷한 차량끼리 ID가 재할당되는 경우는 못 잡는다**는
구조적 사각지대가 있다. 사용자 제안: "ratio가 45→100처럼 순차적으로
증가하는 게 아니라 갑자기 10에서 100이 되는 경우를 제외하면 되지
않을까?" — 1절의 원래 IoU/IoA 아이디어로 돌아가, 이번엔 관찰에 그치지
않고 실제 가드로 써보자는 것.

### 9.2 1단계 — 가설 검증 (관측 전용, 발화 로직 변경 없음)

직전 lookback 실패(5절)가 "검증 없이 로직부터 바꿔서" 터진 사례라,
같은 실수를 피하려고 먼저 데이터부터 봤다. `crossing_trigger_bottomline_test.py`에서
박스-크기 가드의 **취소 동작만 일시적으로 꺼서**(계산은 유지) GANet
3영상 전체를 돌리고 `ratio_jump`(공백 전후 ratio 변화량) 컬럼을 추가
기록했다.

**핵심 결과 — 오탐과 정탐이 뚜렷하게 갈린다:**

| 사례 | 공백 직전 ratio | 공백 직후 ratio | 점프 | 패턴 |
|---|---|---|---|---|
| `#14925`(오탐) | 0.21(33프레임 걸쳐 서서히 0.02→0.21) | **1.0** | 0.79 | 서서히 오르다 공백 만나자 바로 끝으로 순간이동 |
| `#54009`(오탐) | 0.02(시작 직후) | **1.0** | 0.98 | 시작하자마자 거의 바로 100% |
| `#55533`(오탐) | 0.15(시작 직후) | **1.0** | 0.68 | 위와 동일 패턴 |
| `#4`(정탐) | 0.85 | 0.87 | 0.02 | 공백 있어도 거의 안 뜀 |
| `#22816`(정탐) | 0.11 | 0.34 | 0.24 | 뛰어도 그 뒤 수백 프레임 계속 서서히 추가 상승(바로 안 끝남) |

핵심 구분점은 단순 점프 크기가 아니라 **"공백 직후 바로 끝(ratio≈1.0)까지
가버리는지"**다. 추가로 전체 252개 차량으로 범위를 넓혀 ratio_jump가
큰(>0.4) "미지정" 차량 15건을 더 찾았지만, 가드 없이도 전부 다른
안전장치(hold-seconds 등)에 걸려 실제 발화까지는 안 갔다(과잉탐지 위험
낮음). 다만 **에피소드 시작 순간에 공백을 끼고 바로 높은 ratio(0.78~0.96)로
등장**하는 사각지대도 5건 발견 — 전부 박스 크기는 거의 안 변해서 기존
크기 가드로도 못 잡았을 케이스였다(다행히 실제 발화까지는 안 감). 이건
"진행 중" 점프 체크만으로는 못 잡는 영역이라, 시작 순간에도 대칭적 체크가
필요하다는 근거가 됐다. 정상적인 "서서히 접근" 시작은 전부 ratio≤0.36,
이례적 급발진은 전부 0.78↑로 뚜렷하게 갈라져서 임계값 0.5로 분리.

### 9.3 2단계 — 구현 및 교체

박스-크기 가드(`car_size_ref`, 1.5배 기준)를 완전히 제거하고 두 지점에
ratio 점프 체크를 넣었다:

```python
# 진행 중 (에피소드가 이미 열려있는 상태)
ratio_jump_cancel = bool(
    true_detection_gap and ratio >= 0.95 and ratio_jump >= 0.4
)

# 시작 순간 ("직전 ratio"가 없으므로 시작 ratio 자체가 이미 높으면 차단)
if true_detection_gap and start_ratio >= 0.5:
    continue  # 에피소드를 아예 시작하지 않음
```

0.95/0.4/0.5 세 수치 전부 9.2절 실측에 근거하되, 이전 "1.5배" 기준과
마찬가지로 수학적으로 유도한 값은 아니라 경험적 임계값이라는 한계는
동일하게 남는다.

## 11. 번호판 탐지+OCR 이식 (2026-10-16)

### 11.1 계기

사용자 요청: "위반되는 차량은 번호판도 표기되어야 한다." 새로 만들 필요
없이, 이 프로젝트의 **배포용 스크립트** `scripts/05-오토바이헬멧및다인승/
visualize_solid_lane_crossing_v5.3.1.py`에 이미 번호판 탐지+OCR이
구현·배포돼 있었다(기본 활성화, `--no-ocr`로만 끔) — 그걸 실험용
`crossing_trigger_bottomline.py` 계열로 그대로 이식했다.

### 11.2 기존 구현 확인

- 검출 모델 `det-best.pt`가 원래 **4클래스**(0=person, 1=car,
  2=motorcycle, **3=plate_number**)였다 — 이 세션 내내 차량 탐지에만
  써왔지만 번호판 클래스도 이미 들어있어서 추가 모델 불필요.
- OCR은 PaddleOCR(영문, `paddleocr_gpu_cu126` 환경에 `paddleocr==3.7.0`
  설치 확인됨) + `KhoiPaddleOCR` 후처리(크롭 CLAHE 전처리, 숫자/문자
  혼동 보정, `##A ###.##` 형식 정규화).
- `PlateTextStabilizer`가 추적 ID별로 OCR 결과를 모아 최소 3표
  누적되면 빈도×평균신뢰도 기준으로 확정 텍스트를 낸다.
- **핵심 설계**: 번호판 탐지+OCR은 **이미 `flagged_cars`에 들어간(=
  VIOLATION 확정된) 차량에 대해서만** 수행한다 — 매 프레임 모든 차에
  OCR을 돌리면 너무 느려서, 원본(v5.3.1)도 같은 제약을 쓴다.
- 기존 문서 기록(`01. 후처리_개요.md`): v5.3 전체 발화 62건 중
  번호판 확보 성공은 8건(13%) — 드론이 높이 떠서 번호판이 8×3~13×6px로
  작아 탐지는 되지만 OCR 품질이 안 나오는 경우가 대부분.

`PlateTextStabilizer`/`format_plate_text`/`overlap_score`/

## 13. 구간별 처리속도 — 캐시생성+번호판 OCR 포함 최종 재측정

7절의 프로파일링은 (a) GANet의 캐시 생성 비용이 빠져있었고 (b) 번호판
OCR 추가 전 수치였다. `profile_stages.py`에도 번호판 OCR을 포팅해서
(아래 "포팅 중 발견한 버그" 참고) 5분 전체 0816 영상으로 다시 측정,
9절의 GANet 캐시 생성 수치(622.8s, 변동 없음 — OCR은 메인 파이프라인
에만 영향)와 합산한 최종 표:

| 구간 | GANet | YOLO-pose |
|---|---|---|
| 차선 캐시 생성 (1회성) | 622.8s (29.4%) | — (불필요) |
| 차량 탐지+추적 | 397.5s (18.8%) | 345.0s (23.7%) |
| 트래커후처리+차선추적 | 55.0s (2.6%) | 77.8s (5.3%) |
| 에고모션(ORB) | 809.8s (38.3%) | 682.3s (46.8%) |
| 차선 검출 | 1.2s (0.1%, 캐시 읽기) | 135.1s (9.3%, 라이브 추론) |
| 판정로직 | 45.2s (2.1%) | 38.1s (2.6%) |
| 그리기+인코딩 | 174.7s (8.3%) | 170.0s (11.7%) |
| 번호판 OCR | 10.7s (0.5%) | 9.6s (0.7%) |
| **총합** | **2117.0s → 4.24 fps** | **1457.9s → 6.16 fps** |

**결론**: 캐시 생성 비용 포함 시 여전히 **YOLO-pose가 더 빠르다**(4.24 vs
6.16fps, 7절 결론과 동일 방향). 번호판 OCR 자체 비용은 양쪽 다 **1%
미만**(확정된 차량에만 적용하는 설계 덕분)이라 무시할 만하다. 단,
이번 측정은 GPU 8개에 다른 작업 6개와 동시에 돌려서(7절 측정 당시보다
훨씬 무거운 동시 부하) "공통 처리" 구간 숫자들이 ±10~15% 정도 튀었다 —
OCR 때문이 아니라 시스템 자원 경합 때문이므로 절대값보다는 총합 fps
비교·OCR 자체 비중(0.5~0.7%)이 더 신뢰할 수 있는 결론이다.

**포팅 중 발견하고 고친 버그**: `profile_stages.py`에 번호판 OCR을
처음 포팅했을 때 YOLO-pose 쪽이 `GPU count is: 1` 에러로 죽었다 —
PaddleOCR 초기화를 `det_model.track()` 호출 **뒤에** 넣어서, ultralytics가
device= 인자를 처리하며 `CUDA_VISIBLE_DEVICES`를 그 GPU 하나로 좁혀버린
뒤라 PaddleOCR이 원래 GPU 번호를 못 찾았다. `crossing_trigger_bottomline.py`
처럼 **OCR 초기화를 `det_model.track()` 호출보다 먼저** 두는 순서로
고쳐서 해결(같은 순서 문제가 다른 스크립트에도 생기면 똑같이 의심해볼 것).

- ORB 단계 시간: 130.56s → 68.66s (**-47.4%**)
- 다른 단계(탐지/추적/차선/판정/인코딩)는 변화 없음(오차범위 내)

  계산을 피라미드 레벨마다 요청 개수만큼 반복하는 구조와 부합).
- 정확도가 보존되는 이유: 에고모션은 "카메라가 얼마나 움직였는가"(호모그래피

  시작한다.

### 15.4 결론

800으로 확정 승격(`crossing_trigger_bottomline.py:562`, `_test.py` 둘 다
동일). 3영상×2백엔드 전체 재검증 통과(발화 결과 100% 동일, 평균 속도

## 22. `model.track()` vs `model.predict()` 탐지 결과 차이 — 원인 규명 (2026-10-26)

같은 영상·같은 프레임인데 `det_model.track(..., tracker="bytetrack.yaml")`
(파이프라인이 실제 쓰는 방식)이 `det_model.predict()`보다 적게/다르게
탐지하는 현상을 사용자가 포착, 원인 규명을 요청.

**원인**: ByteTrack은 YOLO의 프레임별 탐지 결과를 그대로 반환하지 않고,
**직전 프레임들의 움직임 예측(칼만 필터)과 맞춰보는 자체 연합(association)
단계를 한 번 더** 거친다. 이 매칭에 실패한 탐지는 신뢰도가 높아도 그
프레임 결과에서 **완전히 제외**된다 — `predict()`는 이런 시간적 메모리가
없어 매 프레임 독립적으로 찾은 걸 전부 반환한다.

**검증**:
- 정지 영상(동일 프레임 반복)에서는 `track()`이 `predict()`와 동일하게
  안정적(프레임마다 9개 박스로 동일) — ByteTrack 자체 결함은 아님.
- 실제 주행 영상에서는 `track()` 박스 수가 프레임마다 1~6개로 들쑥날쑥,
  frame 30에서는 `predict()`가 찾은 최고 신뢰도 박스(conf=0.91)가
  `track()` 결과에서 완전히 빠짐(`track()`은 3개뿐, 최고 conf=0.77).
- `bytetrack.yaml` 기본 임계값(`track_high_thresh=0.25` 등)이 파이프라인
  conf=0.25와 같아서 "임계값이 지나치게 엄격해서"라는 가설은 배제.

**결론**: 버그가 아니라 ByteTrack이 추적 연속성을 매 프레임 탐지 재현율보다
우선하는 설계상 특성. 파이프라인/프로덕션 로직 변경 요청은 아직 없음 —
순수 진단성 질문에 대한 답변.

비교용 결과물: `결과영상/yolo/{1-6}_track.mp4`(ByteTrack 적용, ID 라벨
있음), `{1-6}_predict.mp4`(순수 탐지, 추적/ID 없음) — 전부
`setpts=3*PTS`로 실제 재생 속도를 3배 느리게 재인코딩(단순 `fps=30`/`-r`
리샘플링은 재생시간을 바꾸지 않아 속도 문제 해결에는 안 맞음 — 직접
겪은 실수로 확인).
