## 인코딩 병목 분석 → 최적화 적용 (전/후 비교)

최초 측정(아래 "이전 버전")에서 전체 시간의 55~57%가 영상 인코딩
한 단계에 쓰이는 걸 확인했다. 원인 분석 결과 두 가지 문제가 겹쳐 있었다:
(1) `cv2.VideoWriter(mp4v)`가 압축을 거의 안 하는 저효율 소프트웨어
인코더였고, (2) 읽기→전처리→추론→후처리→그리기→인코딩이 **전부 한
스레드에서 순차 실행**돼서 GPU가 다음 프레임을 계산하는 동안 CPU가 놀고
있었다. 두 가지를 모두 고쳤다:

1. **인코더를 GPU 하드웨어 인코더(NVENC, `ffmpeg -c:v h264_nvenc`)로 교체**
2. **인코딩을 별도 스레드/프로세스로 분리해서 메인 루프(추론)와 동시에
   실행**(producer-consumer 큐 구조) — `scripts/04-eval/infer_video_2cls.py`

### 전/후 비교

| | 이전(순차 + cv2 mp4v) | 이후(중첩 + NVENC) | 개선 |
|---|---:|---:|---:|
| res18-2cls 총 처리시간 | 981.9초(16분22초) | **571.7초(9분32초)** | **1.72배** |
| res34-2cls 총 처리시간 | 1023.9초(17분04초) | **552.5초(9분13초)** | **1.85배** |
| 인코더가 병목으로 메인루프를 블로킹한 시간 | (측정 안 됨, 순차라 전부 블로킹) | res18 0.3초 / res34 0.3초 | 사실상 0 — 인코딩이 더 이상 병목이 아님 |
| 결과 파일 용량(원본 mp4v→재인코딩 2단계 필요했음) | 4.7GB → (수동 재인코딩) 2.1GB | 122MB (바로 재생 가능, 재인코딩 불필요) | 약 17~39배 작음 |

> ⚠️ 이 122MB는 사실 "비트레이트를 안 정해서 화질이 심하게 뭉개진" 부작용이었다 — 뒤의 "화질 저하 버그 수정" 참고. 최종 배포된 영상은 화질 복구 후 재생성된 버전(용량 2.16~2.17GB)이다.

**결론: 인코딩 병목은 해결 가능한 문제였고, 실제로 해결했다.** 분석대로
"가장 느린 단계(인코딩) 시간에 수렴"할 것으로 예상했지만, 실측 결과는
이론치(~6~7분)보다 조금 더 걸렸다(~9분대) — 인코더 스레드가 raw 4K
프레임(24.9MB/장)을 계속 파이프로 흘려보내는 작업 자체가 CPU/메모리
대역폭을 쓰기 때문에, 메인 루프의 전처리·후처리 단계가 그만큼 살짝
느려지는(아래 표의 전처리 158→212초, 후처리 80→87초 증가) "중첩의 대가"가
있었다 — 그래도 순수 합산보다는 훨씬 빠르다.

### 단계별 전/후 비교

같은 단계를 "이전(순차+cv2 mp4v)" vs "이후(중첩+NVENC)"로 직접 대조했다.
`인코딩` 행만 의미가 다르다 — 이전은 "실제 인코딩 시간", 이후는 "인코딩
큐가 가득 차서 메인 루프가 멈춘 시간"이다(인코딩 자체는 이제 배경
스레드에서 메인 루프와 동시에 진행되므로 메인 루프 시간에 더는 안
잡힌다 — 작업량이 1/1800로 준 게 아니라 메인 루프에서 빠진 것).

흘려보내는 스레드가 추가되면서 CPU/메모리 대역폭을 나눠 쓰게 된 게
원인으로 보인다. 그래도 인코딩이 통째로 빠진 효과(560초→0)가 다른
단계들이 조금씩 늘어난 것(res18 기준 총 +65.8초)보다 압도적으로 커서
순효과는 res18 1.72배, res34 1.85배 단축이다.

인코딩이 병목에서 빠지고 나니, 이제는 **전처리(리사이즈+정규화, 33~37%)가
가장 큰 비중**을 차지한다 — 다음 최적화를 한다면 이쪽이 다음 타깃이다
(예: `cv2.resize`/정규화를 GPU 텐서 연산으로 옮기거나, 읽기+전처리도
별도 스레드로 분리). 상세 수치는 `속도측정.md`(이후) /
`속도측정_이전(순차+cv2mp4v).md`(이전) 참고.

## 참고

- 전에는 `cv2.VideoWriter(mp4v)` 출력(약 4.7GB)이 용량이 너무 커서
  `ffmpeg libx264(crf20)`로 수동 재인코딩하는 별도 단계가 필요했다(그
  재인코딩 시간은 위 "이전" 수치에 포함 안 됨 — 즉 실제 체감 차이는 표보다
  더 크다). 지금은 NVENC가 바로 압축된 h264(화질 목표 cq=23 지정, ~2.16GB)를
  내놓으므로 이 단계가 통째로 없어졌다.
- 이전 버전 상세 수치는 각 폴더의 `속도측정_이전(순차+cv2mp4v).md`에
  그대로 보관해뒀다(비교용) — 단, 그 파일은 "순차+mp4v vs 중첩+NVENC"
  비교 당시 것이라 평활화는 반영 안 된 상태다.

## 평활화(지그재그 수정) 적용 — 문서 10

이후 예측 차선(특히 점선)이 지그재그로 그려지는 문제를 찾아
`post_process.py`에 Savitzky-Golay 평활화를 추가하고(상세 원인·검증은
문서 10 참고), 영상 2개를 다시 생성했다. 인코딩 최적화는 그대로 유지한
채라 처리시간은 비슷한 범위다: res18 538.2초(8.97분), res34 607.4초
(10.12분) — 직전 측정(571.7초/552.5초) 대비 ±10% 안쪽 변동으로, 평활화
자체의 연산량(Savitzky-Golay는 가벼움)보다는 공유 머신의 실행 시점별
변동으로 보인다.

## 화질 저하 버그 발견과 수정 — 문서 9 §5-1

영상을 직접 재생해보니 전체적으로 화질이 많이 나빠 보인다는 지적을
받았다. 원인은 **NVENC 인코더에 비트레이트/화질 목표를 안 정해서** 기본값
(3.25Mbps)으로 압축된 것 — 이 영상은 3840x2160(4K)인데 4K는 보통
20~50Mbps는 필요하다. 그래서 "용량이 작았던 122MB"는 좋은 압축이 아니라
심하게 뭉개진 결과였다(버스 글자·윤곽이 안 보일 정도).

`-rc vbr -cq 23`(libx264의 `-crf`와 같은 개념, 숫자가 작을수록 고화질)을
추가해서 해결 — cq=23이 이전에 품질을 확인했던 `libx264 crf20` 결과와
비슷한 비트레이트(58Mbps)가 나와서 기본값으로 채택했다. 최종 결과:

| | 수정 전 | 수정 후 |
|---|---:|---:|
| 비트레이트 | 3.25Mbps | res18 61.3Mbps / res34 61.5Mbps |
| 파일 용량 | 122MB | res18 2.16GB / res34 2.17GB |

## 안전지대 줄무늬 혼동으로 인한 큰 폭 지그재그 수정 — 문서 11

평활화 적용 후에도 일부 구간에서 **훨씬 큰 폭(수십~백여 px)**으로 선이
튀는 현상이 추가로 보고됐다. 확인해보니 고속도로 분기/진입 금지 구역의
**안전지대 사선 줄무늬**가 차선처럼 감지돼서, 서로 다른 줄무늬에서 나온
점들이 하나의 차선 그룹으로 잘못 섞여 들어간 것이었다(평활화로는 못 고치는
종류의 문제 — 미세 흔들림이 아니라 애초에 잘못 묶인 점이라).

`post_process.py`에 RANSAC 기반 이상치 제거(`remove_lane_outliers`)를
추가해서 해결 — 실제로 문제가 보고된 프레임(res18 영상 4분7초=247초,
안전지대 줄무늬+경고 기둥 구간)에서 직접 재추론해서 전/후 비교, 지그재그가
완전히 사라진 것을 확인했다(상세 원인·시행착오·검증은 문서 11 참고).

이상치 제거 연산(프레임마다 차선별로 RANSAC 피팅)이 savgol 평활화보다
비용이 커서 처리 시간이 늘었다:

| | 평활화만 적용 | 이상치 제거+평활화(최종) | 변화 |
|---|---:|---:|---:|
| res18-2cls | 532.1초(8.87분) | 787.5초(13.13분) | +48% |
| res34-2cls | 580.2초(9.67분) | 846.1초(14.10분) | +46% |

화질(cq=23, ~61Mbps, ~2.16GB)은 그대로다 — 후처리 로직만 바뀌고 인코딩
설정은 안 건드렸기 때문.

현재 `res18/`, `res34/` 폴더의 영상은 이 수정까지 전부 반영된 **최종
버전**이다(평활화 + 안전지대 줄무늬 이상치 제거 + 화질 복구 모두 적용).
