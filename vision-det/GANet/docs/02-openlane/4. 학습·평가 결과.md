### 1-2. 학습 속도 문제와 조치 (2026-11-18 14:35)

- 증상: 시작 후 약 1시간 동안 iter당 실제 시간이 4초 안팎(로그의 `data_time` 평균 3.2초). GPU 사용률이 대부분 0%였다.
- 원인: DataLoader worker 20개(실험당 4개)가 모두 **CPU 0·40 두 개에만 묶여(affinity)** 있었다. 메인 프로세스는 0-79로 정상. 파이썬 코드(mmcv·mmdet·torch DataLoader·GANet)에서 affinity를 설정하는 곳은 찾지 못했다(원인 코드 미확인).
- 조치: `scripts/02-train/fix_worker_affinity.sh`를 백그라운드로 실행. 30초마다 학습·평가 프로세스의 모든 스레드를 전체 CPU로 되돌린다(epoch마다 새로 생기는 worker도 처리). 학습 재시작 없음.
- 결과: `data_time` 0.08~0.1초, iter당 P3 사용 1.05초 / P3 미사용 0.6초로 smoke test와 같은 속도로 회복. 재시작한 학습은 처음부터 이 스크립트가 붙어 있다.
- 학습이 모두 끝나면 `pkill -f fix_worker_affinity` 로 종료.

## 3. 평가 (스크립트 작성 완료, 학습된 체크포인트로는 아직 미실행)

- 스크립트: `scripts/04-eval/openlane_score_checkpoint.py`(체크포인트 1개), `scripts/04-eval/openlane_score_epochs.sh`(여러 epoch 일괄).
- 방식: 드론용 `score_checkpoint.py`와 같은 점 거리 매칭(공식 CULane IoU 평가 아님). 예측·GT 차선을 y 20px 간격으로 재샘플 → 겹치는 y 구간의 평균 |x 오차| ≤ **20px(원본 1920 기준, 드론 40px@3840과 같은 비율)** 이면 매칭, 가까운 쌍부터 1:1.
- GT: 변환 라벨(`.lines.txt`·`.cls.txt`)을 직접 읽음.
- 지표:
  - [위치] 클래스 무시 P / R / F1 + 매칭된 쌍의 클래스 일치율(`cls_acc`) — 드론 2클래스 점수와 같은 방식
  - [클래스] 같은 클래스끼리만 매칭한 실선·점선 각각의 P / R / F1, 평균 mF1
- 절차: 체크포인트 15개를 **val**로 채점 → best epoch 선택 → 그 하나만 **test**로 최종 평가 (test로 모델을 고르지 않음).
- 결과 저장: `test/<실험>/eval/<split>_epoch<N>.json`, `test/<실험>/eval/<split>_scores.txt`
- 점검: 매칭 함수에 GT를 그대로 넣으면 983/983개 매칭(val 300장). 1 epoch만 학습한 체크포인트로 val 40장을 끝까지 돌려 실행 확인(예측 0개라 점수 0). **학습된 체크포인트로 점수를 낸 적은 아직 없다.**
- 드론 val 점수(F1 0.774 등)와 직접 비교하지 않는다.

```bash
# val: 폴더의 epoch_*.pth 전부
bash /home/hsjeong/workspace/vision-det/GANet/scripts/04-eval/openlane_score_epochs.sh \
  5 015-openlane-res34-2cls-1280-P3del-noSA-noempty-150ep res34_s16_full_2cls_P3del_noSA val
# test: val로 고른 epoch 하나만
bash /home/hsjeong/workspace/vision-det/GANet/scripts/04-eval/openlane_score_epochs.sh \
  5 015-openlane-res34-2cls-1280-P3del-noSA-noempty-150ep res34_s16_full_2cls_P3del_noSA test 140
```
