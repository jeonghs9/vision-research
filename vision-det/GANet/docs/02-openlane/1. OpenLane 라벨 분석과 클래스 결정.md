# OpenLane 라벨 분석과 클래스 결정

> 2026-11-18. 관련: [2. 데이터 변환 (CULane 형식)](2.%20데이터%20변환%20%28CULane%20형식%29.md)
>
> **결론: 2D 차선 학습에는 `lane_lines[].uv`(픽셀 점 좌표)와 `category`만 쓴다. 라벨은 점 리스트이며
> 폴리라인은 점을 직선으로 이은 해석이다. 클래스는 실선/점선 2개로 확정했다(§5).**
>
## 1. 데이터 현황 (2026-11-18, 다운로드 완료)

| 항목 | 값 |
|---|---|
| 이미지 training | 798 segment / 158,081장 / 83GB, 1920×1280, JPEG (≈ quality 95, 4:2:0) |
| 이미지 validation | 202 segment / 39,987장 / 21GB |
| 라벨 JSON training | 798 segment / 157,807개 / 14GB (`raw/lane3d_1000/training/<segment>/`) |
| 라벨 JSON validation | 202 segment / 39,981개 / 3.5GB (`raw/lane3d_1000/validation/<segment>/`, 한 겹 중첩된 것을 training과 같은 모양으로 올림) |
| 이미지·라벨 대응 | 이미지 폴더와 라벨 폴더의 segment 이름이 완전히 일치(training·validation 모두), 깨진 JSON 0 |
| 라벨 없는 이미지 | training 274장(49개 segment), validation 6장(3개 segment) → 목록에서 제외 |
| 원본 라벨 차선 수 | training 659,888개 · validation 162,776개 (라벨 있는 전체 프레임 기준). 차선 0개 프레임 training 15,338 · validation 3,679 |

- segment = 약 20초 영상(10Hz, 연속 프레임 간격의 99.7%가 같은 값). **분할은 반드시 segment 단위**(프레임 단위는 누수).
- **원본 `test` 라벨은 삭제했다.** 별도 test set이 아니라 validation의 시나리오(curve·extreme_weather·intersection·merge_split·night·up_down) 부분집합이었고,
  JSON 42,001개가 모두 validation과 바이트 동일했다(서로 다른 프레임 30,484개, segment 192개 전부 validation 라벨에 있음). 시나리오별 평가가 필요하면 시나리오 목록(txt)을 다시 받아야 한다.
- 이미지 용량 절감 검토(100 segment 시점): 무손실 `jpegtran -optimize` 약 −11%(픽셀 동일), 재압축 q90 약 −28%. **원본에는 적용하지 않았다.**
- 한 segment 안의 연속 프레임은 거의 같은 장면이다(프레임당 평균 0.82m 이동, 정지 위주 segment 다수) → 분할 때 15프레임 간격으로 뽑기로 했다(문서 3).

## 2. 프레임 JSON 구조

```text
intrinsic, extrinsic, pose, file_path,
lane_lines[] = { category, attribute, track_id, uv [[u...],[v...]], xyz, visibility }
```

- **2D 사용 필드: `uv` + `category`** (+ 필요 시 `track_id`). `xyz`·`intrinsic`·`extrinsic`는 3D용이라 쓰지 않는다.
- **`visibility`는 `xyz`(3D 점) 기준이라 `uv` 점 개수와 다르다.** uv 점별 가림 정보로 쓸 수 없다(IndexError로 확인).
- 차선 = **순서 있는 점 리스트**뿐이다. 곡선·폴리라인 타입 필드는 없다. 폴리라인은 그리기/해석이다.
- 점 순서: 99.5%가 가까운 쪽(아래)→먼 쪽(위). 점 간격 중앙값 4.3px. 일부 차선은 점 사이 최대 1,534px 점프가 있다 → 변환 시 점프 처리 필요.

### 남은 쟁점 (미정)

- **연석을 제외해도 프레임은 그대로 둔다** → 연석이 이미지에는 보이는데 라벨에는 없어 모델이 연석을 배경으로 학습한다. 연석을 오검출할 위험이 있고, 평가에서는 "연석 오검출"이 FP로 잡힌다. 필요하면 연석을 ignore 영역으로 처리하는 방법을 검토.
- **category 오라벨 의심**(노란 이중선이 white-solid 등)은 정량 확인 전이라, 합쳐도 실선/점선이 뒤바뀐 경우는 남는다. 실선↔점선 혼동 정도는 별도 확인이 필요.
- **점선·실선 구분이 category에만 있다**: uv 점은 선 전체를 이어 그린 것이라, 점선이어도 한 줄로 이어진 라벨이다 (드론 라벨링 방식과 같은지는 변환 단계에서 확인).
