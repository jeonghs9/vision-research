## 2. 1차 속도 측정 — 파이프라인 단계별 분해

처음에는 "전체 fps"만 재다가, **"전처리/모델 추론 등 구간(단계)별로
쪼개서 보여달라"**는 요청을 받고 스크립트를 고쳐 각 단계(읽기/전처리/
backbone+neck/head+디코딩/후처리/그리기/인코딩)를 `torch.cuda.synchronize()`로
경계를 맞춰 따로 측정했다.

**1차 결과 (순차 실행, `cv2.VideoWriter(mp4v)`)**

| 단계 | res18-2cls | res34-2cls |
|---|---:|---:|
| 영상 디코딩(프레임 읽기) | 58.1초 (5.9%) | 55.6초 (5.4%) |
| 전처리(리사이즈+정규화+GPU 업로드) | 157.5초 (16.0%) | 158.9초 (15.5%) |
| 모델 추론 - backbone+neck | 105.1초 (10.7%) | 142.1초 (13.9%) |
| 모델 추론 - head forward+디코딩 | 13.4초 (1.4%) | 13.2초 (1.3%) |
| 후처리(그룹핑/거리필터/좌표 역변환) | 79.5초 (8.1%) | 84.5초 (8.2%) |
| 결과 그리기(polylines) | 7.9초 (0.8%) | 8.7초 (0.8%) |
| **인코딩(영상 프레임 쓰기)** | **560.3초 (57.1%)** | **560.8초 (54.8%)** |
| **합계** | **981.9초(16분22초)** | **1023.8초(17분04초)** |

순수 GPU 추론만 보면 res18 75fps, res34 57fps로 실시간(30fps)보다 훨씬
빠른데, **전체 처리시간의 절반 이상이 "결과 영상을 mp4로 인코딩해서
저장"하는 단계에서 소모**되고 있었다 — 모델 추론은 전혀 병목이 아니었다.

## 3. 인코딩 병목 원인 분석

"해결 가능한 문제인지 분석해달라"는 요청에 추측이 아니라 **실측**으로
답하기 위해 세 가지를 직접 벤치마크했다(실제 결과 프레임 300장=10초,
3840x2160 기준):

| 방식 | fps | ms/frame | 현재 대비 |
|---|---:|---:|---:|
| 현재: `cv2.VideoWriter(mp4v)` | 16.56 | 60.4 | 기준 |
| `ffmpeg libx264 ultrafast`(소프트웨어) | 20.18 | 49.6 | 1.22배 |
| `ffmpeg libx264 veryfast` | 17.71 | 56.5 | 1.07배 |
| **`ffmpeg h264_nvenc`(GPU 하드웨어)** | **24.38** | **41.0** | **1.47배** |

GPU가 **Tesla V100(2017년 Volta)**이라 NVENC 블록 자체가 최신 소비자용
GPU(RTX 계열)만큼 강력하지 않아서, 코덱만 바꿔서는 1.5배 정도가 한계였다.
합성 테스트 패턴(`testsrc`/단색)으로는 100+ fps가 나왔지만, 실제 교통
영상처럼 디테일이 많은 프레임에서는 압축 작업량 자체가 커서 위 수치가
현실적이었다(합성 벤치마크에 속지 않기 위해 반드시 실제 프레임으로
재검증함).

**더 큰 레버는 코덱이 아니라 구조**였다: 읽기→전처리→추론→후처리→
그리기→인코딩이 **전부 한 스레드에서 순차 실행**되고 있어서, GPU가 다음
프레임을 계산하는 230~240ms 동안 CPU 인코더가 놀고 있었다. 두 작업을
겹치면(overlap) 전체 시간이 "각 단계의 합"이 아니라 "가장 느린 단계
시간"에 수렴할 것으로 예상했다 — res18 기준 compute 합(363초) vs 인코딩
(560초)이므로 겹치면 이론상 ~560초, NVENC까지 더하면 encode도 364초로
줄어 compute와 비슷해져 ~365~400초(6~7분)까지 가능하다는 분석이었다.

## 4. 최적화 적용

`scripts/04-eval/infer_video_2cls.py`에 두 가지를 적용:

1. **인코더를 GPU 하드웨어 인코더로 교체**: `cv2.VideoWriter(mp4v)` →
   `ffmpeg -c:v h264_nvenc`(subprocess로 raw bgr24 프레임을 stdin에 파이프)
2. **인코딩을 별도 스레드로 분리해서 메인 루프와 동시에 실행**:
   `NvencWriter` 클래스가 큐(최대 64프레임)로 메인 스레드와 통신 —
   `write()`는 큐에 넣고 바로 반환(비블로킹에 가까움), 별도 스레드가
   ffmpeg 자식 프로세스에 흘려보낸다. 큐가 가득 차서 `write()`가
   블로킹된 시간(`encode_backpressure`)을 따로 집계해서 "인코딩이 정말
   병목에서 빠졌는지"를 직접 확인할 수 있게 했다.

5초짜리 클립으로 스모크 테스트(정확성 확인: 선 위치/색상 동일, 영상
재생 가능) 후 전체 영상에 재적용.

## 5. 전/후 비교 (실측)

| | 이전(순차+cv2 mp4v) | 이후(중첩+NVENC) | 개선 |
|---|---:|---:|---:|
| res18-2cls 총 처리시간 | 981.9초(16분22초) | **571.7초(9분32초)** | **1.72배** |
| res34-2cls 총 처리시간 | 1023.9초(17분04초) | **552.5초(9분13초)** | **1.85배** |
| 인코딩 때문에 메인 루프가 블로킹된 시간 | (순차라 전부 블로킹) | res18 0.3초 / res34 0.3초 | 사실상 0 — 인코딩이 더 이상 병목이 아님 |
| 결과 파일 용량 | 4.7GB → 수동 재인코딩 2.1GB | 122~124MB(바로 재생 가능) | 17~39배 작음, 재인코딩 단계 자체가 불필요해짐 |

> ⚠️ 위 "122~124MB"는 이 시점엔 "용량이 작아서 좋다"로만 봤는데, 사실은
> 비트레이트를 안 정해서 화질이 심하게 저하된 부작용이었다 — §5-1 참고.

**결론: 인코딩 병목은 해결 가능했고, 실제로 해결했다.** 다만 이론치
(6~7분)보다는 더 걸렸다(9분대) — 인코더 스레드가 4K raw 프레임
(장당 24.9MB)을 계속 파이프로 흘려보내는 작업 자체가 CPU/메모리 대역폭을
쓰기 때문에, "겹쳐 돈다"고 메인 루프의 전처리·후처리가 공짜로 그대로
유지되는 건 아니었다(아래 표에서 전처리 158→212초, 후처리 80→87초로
증가) — 겹침의 대가가 있었지만, 그래도 순차 실행보다는 확실히 빠르다.

### 단계별 전/후 비교

같은 단계를 "이전(순차+cv2 mp4v)" vs "이후(중첩+NVENC)"로 직접 대조했다.
`인코딩` 행만 의미가 다르다는 점에 주의 — 이전은 "실제로 인코딩하는 데
걸린 시간"이고, 이후는 "인코딩 큐가 가득 차서 메인 루프가 멈춘 시간"이다
(인코딩 작업 자체는 이제 배경 스레드에서 메인 루프와 동시에 진행되므로
메인 루프 시간에 더는 안 잡힌다 — 그래서 560초 → 0.3초로 보이는 것이지,
인코딩 작업량 자체가 1/1800로 줄어든 게 아니다).

**해석**:
- **인코딩만 메인 루프에서 통째로 빠지고, 나머지 단계는 전부 소폭
  느려졌다** — 특히 "영상 디코딩(프레임 읽기)"가 가장 많이 늘었다
  (res18 +145%, res34 +84%). 읽기(`cap.read()`)는 CPU로 H.264를
  디코딩하는 작업인데, 이제 같은 프로세스 안에 "NVENC로 raw 4K 프레임
  (장당 24.9MB)을 파이프로 흘려보내는" 배경 스레드가 추가로 돌고 있어서
  CPU/메모리 대역폭을 나눠 쓰게 된 게 원인으로 보인다. 전처리·후처리도
  같은 이유로 9~34% 느려졌다. 다만 res18/res34 두 프로세스가 **GPU는
  각각 다른 걸 쓰지만 같은 머신의 CPU/메모리는 공유**하므로, "이전"과
  "이후" 둘 다 두 프로세스가 동시에 돈 상태라 이 contention 자체는
  새로운 변수가 아니라 "배경 인코딩 스레드 2개가 추가된 것"만 순수하게
  반영한 차이로 봐도 된다.
- 그래도 인코딩이 통째로 빠진 효과(560초 → 0)가 다른 단계들이 조금씩
  늘어난 것(res18 기준 총 +65.8초)보다 압도적으로 커서, **순효과는 res18
  1.72배, res34 1.85배 단축**이다.
- 인코딩이 빠지고 나니 **전처리(리사이즈+정규화)가 33~37%로 가장 큰
  비중**이 됐다 — 다음에 더 줄이고 싶다면 이쪽이 타깃(예: `cv2.resize`/
  정규화를 GPU 텐서 연산으로 옮기거나, 읽기+전처리도 별도 스레드로 분리).

## 5-1. 화질 저하 버그 발견과 수정

영상을 직접 돌려보니 전체적으로 화질이 눈에 띄게 나빠 보인다는 지적을
받았다. 확인해보니 **파일이 작아진 게(122MB) "잘 압축된 것"이 아니라
"너무 세게 눌러서 망가진 것"**이었다.

**원인**: `NvencWriter`에서 ffmpeg에 `-c:v h264_nvenc`만 넘기고 비트레이트/
화질 목표를 하나도 안 정했다. 이러면 nvenc가 기본값으로 떨어지는데, 실측
결과 **초당 3.25Mbps**였다 — 이 영상은 **3840x2160(4K)**인데, 4K는 보통
좋은 화질을 유지하려면 20~50Mbps는 필요하다. 필요한 용량의 1/10도 안 되게
욱여넣은 것이니 뭉개질 수밖에 없었다(문서 앞부분에서 수동으로 재인코딩할
때 썼던 `libx264 -crf 20`은 "화질 목표"를 지정하는 방식이라 결과적으로
~58Mbps가 나왔던 것과 대조적 — NVENC로 바꾸면서 이 설정을 빠뜨렸다).

**수정**: ffmpeg 명령에 `-rc vbr -cq 23 -b:v 0 -maxrate 80M -bufsize 80M`
추가 — `-cq`(constant quality)가 libx264의 `-crf`와 같은 개념으로, 숫자가
작을수록 고화질이다. cq 19/21/23/25를 실제로 돌려보고 비트레이트를
비교했다:

| cq | 비트레이트 | 전체 영상(296초) 예상 용량 |
|---:|---:|---:|
| 19 | 83Mbps | ~2.6GB (너무 큼, maxrate 상한에 걸림) |
| **23** | **58Mbps** | **~2.1GB (crf20 기준과 거의 동일)** |
| 25 | 48Mbps | ~1.8GB |

**cq=23**을 기본값으로 채택 — 앞서 품질을 확인했던 `crf20` 결과와 비트레이트가
거의 같아서, 같은 수준의 화질을 보장한다. 버스 주차장처럼 디테일이 많은
영역을 확대해서 수정 전(3.25Mbps)/후(58Mbps)를 직접 비교 — 수정 전은
버스 글자·윤곽이 뭉개져 있었고 수정 후는 선명했다(육안 확인 완료).

수정 후 최종 결과: **res18 61.3Mbps/2.16GB, res34 61.5Mbps/2.17GB**(§6
결과물 경로의 파일이 이 버전). 처리 속도는 cq를 올려도 거의 안 바뀐다
(NVENC는 압축 품질을 올려도 하드웨어 인코딩 자체의 속도 부담이 크지
않음) — res18 532.1초(8.87분), res34 580.2초(9.67분)로 §5의 측정과
비슷한 범위.
