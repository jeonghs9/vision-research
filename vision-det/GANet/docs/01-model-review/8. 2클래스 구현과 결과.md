# 2클래스(실선·점선) 구현과 결과

>
> **결론: 문서 6 계획대로 구현 완료, res18/res34 둘 다 1클래스와 동일한

> 전체 정량평가로 res18은 epoch120(F1 0.738), res34는 epoch130(F1 0.749)을

> `models/drone-ganet-res34-2cls-v1.pth`로 승격 완료.**

## 1. 구현 범위 (문서 6 대비 실제 변경)

문서 6에서 4곳으로 추정했던 변경 지점을, 코드를 다시 읽으며 좁혔다 —
**`ganetloss.py`의 focal loss가 이미 채널 수에 무관하게(`(B,C,H,W)` 그대로
sum) 동작**해서 loss 쪽은 손댈 필요가 없었다. 실제 수정은 다음 6곳:

1. `scripts/01-data/polyline_to_culane.py` — `--write-class` 플래그 추가,
   `.lines.txt`와 같은 순서로 `.cls.txt`(1=실선, 2=점선) 추가 기록(additive,
   기존 출력 비파괴)
2. `projects/plugin/datasets/culane_dataset_2cls.py` (신규) — `CulaneDataset`
   상속, `load_labels()`만 오버라이드해서 `.cls.txt`를 읽어 실제 `id_classes`
   반환
3. `projects/plugin/datasets/pipelines/lane_target_collect.py` —
   `CollectLanePoints(num_classes=1)` 파라미터화, heatmap을
   `(num_classes,H,W)`로 확장하고 차선마다 자기 클래스 채널에 그림
4. `projects/plugin/models/ganet_head.py` — `ktdet_decode_fast`를 클래스별
   루프로 재구성(채널 하나씩 슬라이스해서 기존 수식 그대로 재사용),
   `[(class_id, root_center_arr, kpt_seeds), ...]` 리스트 반환
5. `projects/plugin/core/post_process.py` — `PostProcessor.__call__`이 클래스별
   리스트를 받아 각각 그룹핑·필터링 후 합치고, `final_dict_list`에
   `result_classes`(4번째 원소) 추가
6. `projects/plugin/models/ganet.py` — `vis_one()` 언패킹 4개로 변경, 클래스별
   고정색(실선=초록 `(0,220,0)`, 점선=빨강 `(0,0,220)`, **BGR 순서** — `mmcv.imread`가
   BGR이라 처음에 RGB로 넣었다가 빨강이 파랑으로 보이는 버그를 실측 후 수정)

모든 변경이 "클래스 수만큼 반복"하는 형태라 `num_classes=1`이면 1클래스
경로와 수학적으로 동일 — 공유 코드 변경 후 1클래스 config로 회귀 스모크
테스트를 다시 돌려 확인했다.

신규 config: `projects/cfgs/drone/res18_s8_full_2cls.py`,
`res34_s8_full_2cls.py` — `res18_s8_full.py`/`res34_s8_full.py`와 해상도·
batch·lr·epoch 전부 동일, `num_lane_classes=2`와 `dataset_type=CulaneDataset2Cls`만
다르다.

## 2. 스모크 테스트

1epoch 스모크 테스트(GPU0)로 다음을 확인:

- `kpts_hm` shape이 `(2, H, W)`로 정상 출력
- loss가 1클래스 때와 비슷한 패턴으로 감소(채널 2개가 됐다고 손실 스케일이
  깨지지 않음)
- `visualize_checkpoint.py` 결과에서 실선(초록)/점선(빨강) 색 구분이 실제로
  됨
- 1클래스 config(`res18_s8_full.py`) 회귀 스모크 — 기존과 동일한 shape/동작,
  시각화 색도 여전히 인덱스 기반(클래스색으로 안 바뀜) 확인

## 3. 본학습 및 epoch별 관찰

res18-2cls(GPU1), res34-2cls(GPU2) 150epoch 동시 진행, 10epoch마다 자동
시각화(`output/02-cls2-에폭별val확인/{res18,res34}/epNN/`)로 관찰:

- **`000325.jpg`(세로형 긴 차선, 2실선+1점선)**: epoch10부터 150까지 두
  백본 모두 안정적으로 초록2+빨강1로 깔끔하게 잡힘. res34 epoch100에서
  딱 한 번 오탐(실선 자리에 빨간선 겹침)이 있었으나 epoch110에서 바로
  사라짐 — 일시적 노이즈로 판단.
- **`000100.jpg`(짧고 가로로 누운 차선)**: epoch10~150 전 구간에서 두 백본
  모두 최종 예측이 비어있음. epoch60 전후부터 vc(virtual center) 패널에
  후보점이 조금씩 생기기 시작했지만 `points_thr`(10점)를 끝까지 못 넘김.
  - 원인 분석(직접 heatmap 프로빙, `.lines.txt` 기하 분석): (1) 차선 길이가
    700~1080px/36~55점으로 짧고(000325는 2100px+/106~108점), (2) 차선이
    거의 가로(width/height 비 2.0~3.43, 000325는 0.03~0.33)로 누워있음 —
    GANet의 `ploy_fitting_cube()`가 y를 독립변수로 쓰는 스플라인 피팅이라
    가로 차선에 불리하고, "전방 카메라+세로로 뻗는 차선" 가정(문서 1에서
    이미 리스크로 지적)이 실제로 발목을 잡는 사례로 확인됨.
  - kpt_thr(0.4)/points_thr(10) 메커니즘: heatmap 각 칸의 확신도가
    kpt_thr를 넘어야 후보점이 되고(1차 필터), 묶인 후보점 그룹의 점 개수가
    points_thr를 넘어야 최종 선으로 인정(2차 필터). 000100은 class1 최고
    확신도가 0.478(턱걸이)이고 40% 넘는 칸이 6개뿐이라 애초에 그룹을
    키워도 10개를 못 넘김.

## 5. 1클래스 대비 비교

| | 1클래스 최고 | 2클래스 최고 | 차이 |
|---|---:|---:|---:|
| res18 | epoch140, F1 **0.758** | epoch120, F1 **0.738** | -0.020 |
| res34 | epoch150, F1 **0.758** | epoch130, F1 **0.749** | -0.009 |

두 백본 다 2클래스에서 F1이 소폭(0.01~0.02) 하락 — heatmap을 2채널로
나눠 쓰면서 생긴 용량 손해로 추정되며, 심각한 성능 붕괴는 아니다. res34가
res18보다 하락폭이 작아(-0.009 vs -0.020), 백본이 클수록 클래스 분리
부담을 더 잘 흡수하는 것으로 보인다. 두 백본 다 80epoch 이후 수렴하고
그 이후는 ±0.01~0.03 범위에서 등락하는 패턴도 1클래스 때와 동일하다.
